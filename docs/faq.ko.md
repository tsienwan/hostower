## 호스트 연결

### SSH 자격 증명에 root를 쓸 수 없는 이유는 무엇인가요?

Hostower는 "모든 호스트의 열쇠"와 같으므로, 호스트 쪽에도 Hostower 자신이 열 수 없는 문이 하나 더 있어야 합니다.

1. **패널이 뚫렸을 때 피해 제한**: 데이터베이스와 마스터 키가 유출되면 공격자는 Hostower가 저장한 개인 키를 얻을 수 있습니다. root의 개인 키는 곧 호스트 전체를 장악한다는 뜻이지만, 제한된 계정은 sudo가 허용하는 일만 할 수 있습니다.
2. **등급 판정은 완벽할 수 없음**: 판정 엔진은 shell을 구문 분석해야 하므로, 미처 생각하지 못한 우회 작성법이 언제든 있을 수 있습니다. sudo 제한은 호스트 시스템이 직접 적용하므로 독립적인 두 번째 안전장치가 됩니다.
3. **대화형 터미널은 명령을 하나씩 판정하지 않음**: 터미널을 열려면 L2 승인이 필요하고 전 과정이 녹화되지만, 그 안에서 입력하는 명령은 더 이상 하나씩 판정하지 않습니다. root로 로그인하면 한 번 승인된 뒤에는 무엇이든 할 수 있습니다.
4. **운영 관행**: 많은 시스템이 기본적으로 root의 SSH 로그인을 금지합니다. 전용 계정으로 로그인하면 호스트의 `auth.log`와 sudo 로그에서 어떤 작업을 Hostower가 했는지 구분할 수 있습니다.

이것은 강제 제한입니다. 사용자 이름에 `root`를 입력하면 바로 거부됩니다.

### Hostower 전용 계정은 어떻게 만드나요?

관리 대상 호스트에서 root로 실행합니다.

```bash
useradd -m -s /bin/bash hostower
mkdir -p /home/hostower/.ssh
echo 'ssh-ed25519 AAAA… (공개 키)' >> /home/hostower/.ssh/authorized_keys
chown -R hostower:hostower /home/hostower/.ssh
chmod 700 /home/hostower/.ssh
chmod 600 /home/hostower/.ssh/authorized_keys
```

그런 다음 다음 절에 따라 sudo를 설정하고, Hostower의 **자격 증명**에서 SSH 자격 증명을 추가합니다. 사용자 이름에는 `hostower`를, 개인 키에는 위 공개 키와 짝이 되는 키(`-----BEGIN`부터 `-----END`까지 전체)를 입력합니다.

### root는 이미 키로 로그인할 수 있는데, 새 계정에도 키를 다시 설정해야 하나요?

네. 공개 키는 계정별로 둡니다. 각 계정은 자기 홈 디렉터리의 `~/.ssh/authorized_keys`에 있는 공개 키만 인정하며, `/root/.ssh/authorized_keys`는 root에게만 유효합니다.

두 가지 방법이 있습니다.

- **권장: Hostower용 키를 따로 생성합니다.** root는 원래 쓰던 키를 계속 사용하고, 그 개인 키는 Hostower에 넘기지 않고 본인만 보관합니다.

  ```bash
  ssh-keygen -t ed25519 -f hostower_key -N ""
  ```

  `hostower_key.pub`의 내용을 hostower 계정의 `authorized_keys`에 넣고, `hostower_key`의 내용을 Hostower의 자격 증명에 입력합니다.
- **간편: root의 공개 키를 복사합니다.**

  ```bash
  cp /root/.ssh/authorized_keys /home/hostower/.ssh/
  ```

  대가는 같은 개인 키로 hostower와 root 모두에 로그인할 수 있다는 점입니다. Hostower에서 유출되면 곧 root가 유출된 것과 같습니다. 이렇게 한다면 `/etc/ssh/sshd_config`에서 `PermitRootLogin no`를 설정하고 sshd를 재시작하는 것이 좋습니다. 바꾸기 전에 hostower로 로그인할 수 있고 `sudo -i`로 root로 전환할 수 있는지 먼저 확인해야 스스로 잠기는 일을 피할 수 있습니다.

### 개인 키에 대응하는 공개 키가 무엇인지 기억나지 않아요

개인 키가 저장된 컴퓨터에서 공개 키를 추출합니다.

```bash
ssh-keygen -y -f 개인_키_파일
```

### `ssh: unable to authenticate, attempted methods [none publickey]` 오류가 납니다

네트워크는 이미 연결되었지만 호스트가 이 개인 키를 인정하지 않는다는 뜻입니다. 흔한 순서대로 확인합니다.

1. **공개 키가 이 계정의 `authorized_keys`에 들어 있지 않음.** `sudo cat /home/hostower/.ssh/authorized_keys`로 확인합니다. 파일이 없다고 나오면 아직 넣지 않은 것입니다.
2. **권한이 너무 넓음**: sshd는 이런 공개 키를 그냥 무시합니다. `.ssh` 디렉터리는 700, `authorized_keys`는 600이어야 하며, 소유자는 모두 해당 계정이어야 합니다.
3. **사용자 이름이 틀림**: 자격 증명에 입력한 사용자 이름은 공개 키가 있는 계정과 같아야 합니다.
4. **개인 키를 불완전하게 붙여 넣음**: 첫 줄이나 마지막 줄이 빠졌거나, 줄바꿈이 사라졌습니다.

자신의 컴퓨터에서 확인해 봅니다.

```bash
ssh -i 개인_키_파일 -o IdentitiesOnly=yes hostower@192.0.2.10
```

여기서도 로그인되지 않으면 호스트의 sshd 로그를 봅니다.

```bash
sudo journalctl -u ssh -u sshd -n 30 --no-pager
```

로그에 `bad ownership or modes`가 나오면 권한 문제이고, `Invalid user`가 나오면 사용자 이름이 틀린 것입니다. 본인은 로그인되는데 Hostower만 안 된다면 **자격 증명**에서 개인 키를 다시 붙여 넣으세요.

설정을 마친 뒤에는 따로 할 일이 없습니다. Hostower가 자동으로 다시 연결합니다.

### "호스트의 공개 키가 처음 연결할 때와 다릅니다" 오류가 납니다

Hostower는 호스트에 처음 연결할 때 그 공개 키를 기록해 두고, 이후 일치하지 않으면 연결을 거부합니다. 누군가 중간에서 가장하고 있을 수도 있고, 호스트에 시스템을 다시 설치했을 수도 있습니다. 재설치임을 확인했다면 Hostower를 실행하는 머신에서 이전 기록을 지웁니다.

```bash
hostower hostkey forget web-1
```

## sudo

### 계정에 sudo를 설정해야 하나요? 어떻게 설정하나요?

패키지 설치, Docker 설치, 방화벽 변경 같은 작업에는 모두 root가 필요합니다. root가 아닌 계정은 `sudo -n`(암호 없이 실행하며, 암호 입력을 기다리며 멈추지 않음)을 사용합니다. 설정 방법은 두 가지입니다.

**방안 1: 모든 명령을 암호 없이 실행(가장 간편)**

```bash
echo 'hostower ALL=(ALL) NOPASSWD: ALL' > /etc/sudoers.d/hostower
chmod 440 /etc/sudoers.d/hostower
visudo -c
```

`visudo -c`는 반드시 실행하고, `parsed OK`가 표시되어야 문법이 올바른 것입니다. sudoers를 잘못 작성하면 sudo 전체를 쓸 수 없게 될 수도 있습니다.

이렇게 설정하면 이 계정은 권한 면에서 root에 가깝습니다. 보호는 Hostower 자체에서 나옵니다. 모든 변경은 등급 판정을 거치고, 사용자의 승인을 받아야 하며, 감사에 기록됩니다. root로 직접 로그인하는 것과 비교하면 두 가지 장점이 여전히 남습니다. root의 SSH 로그인을 금지할 수 있고, 로그에서 어떤 작업이 Hostower에서 왔는지 구분할 수 있습니다.

**방안 2: 일부 명령만 허용(허용 목록)**

Hostower에게 몇 가지 일만 맡기려는 경우에 적합합니다. 예를 들면 다음과 같습니다.

```
hostower ALL=(root) NOPASSWD: /usr/bin/systemctl, /usr/bin/journalctl
```

주의할 점은 `env`, `tee`, `docker`, `sh` 같은 명령을 허용 목록에 넣으면 이를 통해 임의의 명령을 실행하거나 임의의 파일을 쓸 수 있어 방안 1과 효과가 같아진다는 것입니다. 그리고 **Docker 설치** 같은 기능은 바로 이런 명령을 써야 하므로 방안 1과 함께만 사용할 수 있습니다.

**적용되었는지 확인**:

```bash
su - hostower -c 'sudo -n true && echo ok'
```

### 오래된 시스템에서 `you must have a tty` 오류가 납니다

CentOS 7 같은 오래된 시스템의 sudoers에는 `Defaults requiretty`가 있을 수 있습니다. 이 계정에 대해서만 따로 꺼야 합니다.

```bash
echo 'Defaults:hostower !requiretty' >> /etc/sudoers.d/hostower
visudo -c
```

## Docker와 컨테이너 앱

### 앱을 설치할 때 "이 호스트에 Docker Compose v2가 없습니다" 오류가 납니다

호스트에 Docker가 설치되어 있지 않거나, Docker는 있지만 `docker compose` 플러그인이 없는 경우입니다. 이제 앱 설치 대화 상자와 **컨테이너** 페이지에서 먼저 확인하며, 빠진 것이 있으면 안내와 함께 **Docker 설치** 버튼을 보여 줍니다.

- 버튼을 누르면 요청(L1)이 생성됩니다. 승인할 때 이 호스트에 맞게 조립된 각 단계의 명령을 볼 수 있으며, 승인한 뒤에야 실행됩니다.
- Debian, Ubuntu, Raspbian, CentOS 계열(Rocky, AlmaLinux, RHEL)과 Fedora는 Docker 공식 저장소에서 설치하고, Alpine, Arch, openSUSE는 시스템 자체 저장소를 사용합니다. "스크립트를 내려받아 바로 실행"하는 방식(`curl … | sh`)은 쓰지 않습니다.
- Docker는 이미 있고 Compose만 없으면 Compose 플러그인만 설치합니다.
- 계정이 root이거나 암호 없이 sudo를 쓸 수 있어야 하며(이전 절 참고), 그렇지 않으면 버튼이 나타나지 않습니다.
- 시스템을 인식하지 못하면 Docker 공식 문서에 따라 직접 설치하세요.

### Docker를 설치한 뒤 컨테이너 페이지에 `permission denied … docker.sock`이 표시됩니다

로그인 계정이 `docker` 그룹에 속해 있지 않습니다. Hostower는 스스로를 이 그룹에 추가하지 않습니다. docker 그룹에 들어가는 것은 root 권한을 얻는 것과 같으므로, 이 단계는 사람이 호스트에서 직접 해야 합니다.

1. 호스트에서 root로 실행합니다(컨테이너 페이지에서 이 명령을 바로 복사할 수 있습니다).

   ```bash
   usermod -aG docker hostower
   ```

2. 컨테이너 페이지로 돌아가 **다시 연결**을 클릭합니다.

계정을 새 그룹에 추가한 뒤에는 다시 로그인해야 적용됩니다. "다시 연결"은 Hostower와 이 호스트 사이의 연결을 끊고 한 번 다시 로그인하므로 Hostower를 재시작할 필요가 없습니다. 주의: 연결을 끊을 때 이 호스트에서 실행 중인 명령은 중단됩니다.

호스트 모드의 `local` 호스트는 예외입니다. Hostower 프로세스 자신의 신원을 사용하므로 Hostower를 재시작해야 적용됩니다.

### 컨테이너 이름이 `3x-ui-3x-ui-1`처럼 반복되는 이유는 무엇인가요?

Docker Compose의 기본 명명 방식(프로젝트 이름-서비스 이름-번호)이며, 이전 버전에서 이런 이름이 생겼습니다. 이제 서비스가 하나뿐인 앱은 컨테이너 이름이 인스턴스 이름과 같고, 서비스가 여러 개인 앱은 컨테이너 이름이 "인스턴스 이름-서비스 이름"입니다.

이미 설치된 앱은 **설치됨**에서 설정을 한 번 바꾸거나 한 번 업데이트하면 컨테이너가 새 이름으로 바뀌며, 데이터 디렉터리는 영향을 받지 않습니다. 호스트에 같은 이름이지만 Hostower가 설치하지 않은 컨테이너가 이미 있으면 배포할 때 이름 충돌 오류가 나므로, 먼저 그 컨테이너를 처리해야 합니다.

### 앱을 설치했는데 어디서 여나요? 초기 계정과 비밀번호는 무엇인가요?

**앱 → 설치됨**에서 해당 행의 로켓 아이콘(**시작 가이드**)을 클릭합니다. 접속 주소(바로 클릭해서 열 수 있습니다), 초기 계정에 대한 설명, 이어서 해야 할 몇 가지 단계가 들어 있습니다. 설치 요청이 성공적으로 실행된 뒤에는 요청 상세 페이지에도 같은 입구가 있습니다.

- 초기 비밀번호를 설치할 때 정할 수 있는 앱(OpenList의 admin 비밀번호, LiteLLM의 마스터 키, 데이터베이스 비밀번호)은 설치할 때 고른 앱 시크릿이 곧 비밀번호입니다.
- 처음 열 때 관리자를 직접 만드는 앱(Uptime Kuma, Portainer, Open WebUI, New API, n8n)은 초기 계정이 없습니다. 설치한 뒤 가능한 한 빨리 열어 가입을 마치세요.
- 3x-ui의 초기 사용자 이름과 비밀번호는 처음 시작할 때 무작위로 생성되며 컨테이너 로그에 한 번만 나타납니다. 시작 가이드에서 **초기 사용자 이름과 비밀번호 읽기**를 클릭하면 패널이 읽기 전용 조회 한 번으로 그 줄을 읽어 옵니다. 컨테이너를 다시 만든 뒤에는 로그에 남아 있지 않으므로, 이때는 가이드에 나온 명령으로 호스트의 터미널에서 다시 설정하세요.

주소가 열리지 않으면 먼저 수신 주소가 `127.0.0.1`인지 확인하고(호스트 자체에서만 접근할 수 있으므로 리버스 프록시를 설정하거나 **설정 변경**에서 `0.0.0.0`으로 바꿔야 합니다), 그다음 호스트 방화벽과 클라우드 업체의 보안 그룹이 이 포트를 허용하는지 확인하세요.

### '환경' 페이지의 '제한됨', '연결 불가'는 무슨 뜻인가요?

호스트 페이지의 **환경**과 **앱 → 환경**은 이 호스트에서 읽기 전용 요청을 한꺼번에 보내 각 서비스가 어떻게 응답하는지 봅니다.

- **대형 모델 API**(OpenAI, Anthropic, Google Gemini, xAI, DeepSeek): 키 없이 요청합니다. "키가 없다"고 응답하면 **사용 가능**이며, 키를 넣으면 호출할 수 있습니다. 출구가 있는 국가나 지역을 이유로 거부하면 **제한됨**입니다. 다른 지역의 호스트로 바꾸거나 LiteLLM, New API 같은 게이트웨이를 거쳐 전달하세요.
- **웹사이트와 스트리밍**(Google, YouTube, Netflix, Disney+, TikTok, Facebook, X, ChatGPT 웹 버전 등): 정상적으로 열리면 **사용 가능**, 거부되거나 "해당 지역에서는 서비스를 제공하지 않습니다" 페이지로 넘어가면 **제한됨**입니다. YouTube와 Netflix는 어느 지역으로 잡히는지도 표시합니다. Netflix는 오리지널이 아닌 작품 하나로 판단하며, "오리지널 작품만 볼 수 있습니다"는 그 지역의 콘텐츠 목록이 이 주소에는 열려 있지 않다는 뜻입니다.
- **연결 불가**: 8초 안에 연결되지 않았습니다. 네트워크에서 막혔을 수도 있고, 호스트에 `curl`이 없을 수도 있습니다.
- **불확실**: 연결은 되었지만 응답이 위의 어느 경우도 아니어서 판단할 수 없습니다.

여기서는 서비스가 어떻게 응답하는지만 보며, 어떤 계정에도 로그인하지 않습니다. 각 업체의 웹 버전과 구독 로그인에는 별도의 지역 및 위험 관리 규칙이 있으므로, API를 사용할 수 있거나 사이트가 열린다고 해서 계정도 반드시 쓸 수 있는 것은 아닙니다. 같은 페이지에는 호스트에 설치된 AI 명령줄 도구(Claude Code, Codex CLI, Gemini CLI 등)와 실행 환경도 나열됩니다. 버전은 설치 디렉터리에서 읽으며, 이 프로그램들을 실행하지는 않습니다.

### '출구 IP'의 유형과 위험 점수는 무엇인가요? 정확한가요?

웹사이트가 보는 것은 호스트의 출구 주소입니다. 그 주소가 어떤 유형인지, 나쁜 기록이 있는지에 따라 제한을 받는지, 사람 확인을 자주 해야 하는지가 달라집니다.

- **유형**: 데이터 센터, 가정용 인터넷, 기업 전용선, 모바일 네트워크 등. VPS는 대개 데이터 센터 주소여서 스트리밍에서는 오리지널 작품만 볼 수 있는 경우가 많고, AI 서비스의 구독 로그인도 위험 관리에 걸리기 쉽습니다.
- **프록시 표시**: 정보 데이터베이스가 그 주소를 프록시나 VPN 출구로 표시했는지 여부입니다.
- **위험 점수**: 0부터 100까지이며, 높을수록 이 주소나 주소가 속한 대역에 악용 기록이 많다는 뜻입니다. 33 미만은 낮음, 66 초과는 높음으로 봅니다.
- 그 밖에 운영 주체(ASN), 위치, IPv6 출구가 있는지, Cloudflare WARP를 거치는지도 표시합니다.

이 정보는 호스트가 직접 공개 IP 정보 데이터베이스(proxycheck.io)에 자신의 출구 주소를 조회해 얻은 것으로, 참고용일 뿐입니다. 데이터베이스마다 결론이 다를 수 있고, 각 웹사이트의 위험 관리가 이것만 보는 것도 아닙니다. 조회되지 않으면 "찾지 못했습니다"로 표시되며 다른 확인에는 영향을 주지 않습니다.

### AI 도구마다 token을 얼마나 썼는지 집계하려면 어떻게 하나요?

LiteLLM이나 New API를 설치하고(앱 카탈로그의 **AI 도구**에 있습니다), Claude Code, Codex CLI 등 도구의 API 주소를 모두 그쪽으로 향하게 한 다음, 도구마다 또는 사람마다 키를 따로 발급하세요. 키별, 모델별 호출 횟수, token 사용량, 비용은 게이트웨이 자체의 관리 화면에서 볼 수 있습니다. Hostower 자체는 모델 요청을 중계하지도 기록하지도 않습니다.

### 고정 버전 태그(예: `v3.9.0`)를 쓰는 이미지는 어떻게 업데이트하나요?

컨테이너 페이지는 이미지 레지스트리의 태그 목록을 읽습니다.

- 같은 메이저 버전 안에 새 버전이 있으면 "새 버전 vX"를 표시하며, 업데이트를 누르면 새 태그로 바꾸고 원래 설정대로 컨테이너를 다시 만듭니다.
- 메이저 버전을 넘는 새 버전은 알려 주기만 하고 자동으로 바꾸지 않습니다. 메이저 버전 업그레이드에는 호환되지 않는 변경이 있을 수 있으므로 먼저 릴리스 노트를 확인하세요.

## 사이트, 인증서와 Fail2ban

### Caddy와 Nginx 중 무엇을 고를까요?

호스트 상세의 '네트워크' 페이지에서 둘 다 원클릭으로 설치할 수 있고(시스템 저장소 사용), 리버스 프록시, 정적 디렉터리, 리디렉션 세 가지 사이트를 만들 수 있습니다.

- **Caddy**: HTTPS 인증서를 자동으로 발급·갱신해 가장 손이 덜 갑니다. 특별한 이유가 없으면 이쪽을 고르세요.
- **Nginx**: Nginx에 익숙하거나 호스트에 이미 Nginx 설정이 있을 때 고르세요. 인증서는 Let's Encrypt로 자동 발급(Hostower가 certbot도 설치하며 certbot이 정기적으로 갱신)하거나 호스트에 있는 기존 인증서 경로를 지정합니다.

둘 다 80, 443 포트를 쓰므로 Hostower는 호스트마다 하나만 설치합니다. Hostower는 자신이 쓴 파일(`/etc/caddy/sites.d/`, `/etc/nginx/conf.d/hostower-*.conf`)만 관리하고 호스트에 원래 있던 설정은 건드리지 않습니다.

### Let's Encrypt 인증서 발급에 실패했습니다

실패하면 사이트는 우선 HTTP로 제공되고 다른 사이트에는 영향이 없습니다. 흔한 원인:

- 도메인이 아직 이 호스트를 가리키지 않습니다(또는 DNS 변경이 아직 반영되지 않았습니다).
- 외부에서 80 포트에 접근할 수 없습니다: 호스트 방화벽과 클라우드 업체의 보안 그룹 모두 80과 443을 허용해야 합니다.
- 다른 프로그램이 80 포트를 쓰고 있습니다.
- 같은 도메인으로 짧은 시간에 너무 많이 신청해 Let's Encrypt 한도(같은 도메인 조합당 주 5장)에 걸렸습니다.

원인을 해결한 뒤 사이트를 내렸다가 다시 추가하세요.

### 443 포트를 이미 3x-ui(Xray)가 쓰고 있습니다

두 프로그램이 같은 포트에서 동시에 수신할 수는 없습니다. Xray 인바운드를 다른 포트로 옮기거나, 사이트 주소에 포트를 붙이세요(예: `app.example.com:8443`). 후자의 경우 Nginx는 기존 인증서만 쓸 수 있고 Caddy는 여전히 자동으로 발급받을 수 있습니다.

### Fail2ban이 저나 Hostower를 차단하지 않을까요?

허용 목록에는 항상 루프백 주소와 Hostower가 이 호스트에 접속하는 주소가 들어 있고, Hostower는 키로 로그인하므로 실패 기록도 남기지 않습니다. 본인의 공인 IP가 바뀐다면 자주 쓰는 네트워크를 허용 목록에 추가하세요.

그래도 차단되었다면 '네트워크' 페이지에서 해당 IP 옆의 차단 해제를 누르거나, 다른 주소나 클라우드 업체 콘솔에서 로그인해 다음을 실행하세요:

```bash
sudo fail2ban-client set sshd unbanip 203.0.113.7
```

Fail2ban은 방화벽 규칙을 바꾸므로 설치, 설정 변경, 차단 해제는 모두 고위험 작업(L2)입니다. 웹에서만 승인할 수 있고 승인할 때 신원을 다시 확인합니다.

## 고급 수집

### 고급 수집을 설치한 뒤 페이지가 갱신되기까지 얼마나 걸리나요?

승인되어 실행이 성공하면 Hostower는 곧바로 이 호스트의 샘플링을 다시 연결하므로, 보통 몇 초 안에 "고급 수집 버전 번호"와 프로세스 순위를 볼 수 있습니다. 기다리는 동안 버튼은 "승인 대기", "설치 중…", "수집 방식 전환 중…"을 차례로 표시하여 중복 제출을 막습니다. 제거할 때도 마찬가지입니다.

## 트래픽 한도

### 패널의 월 트래픽이 제공업체 패널과 다릅니다

호스트 페이지의 "트래픽" 카드와 개요의 "트래픽 순위"에 나오는 수치는 각 인터페이스의 누적 카운터에서 다음 기준으로 셉니다.

- **업링크 인터페이스만 셉니다.** WireGuard, OpenVPN, Tailscale 같은 터널, `br0`, `vmbr0` 같은 브리지, `eth0.100` 같은 VLAN 하위 인터페이스, 본딩 멤버는 같은 트래픽이므로 중복 집계하지 않습니다. `lo`, `docker0`, `veth…` 같은 가상 인터페이스도 제외합니다. 특정 인터페이스만으로 과금하려면 "한도 설정"의 "집계할 인터페이스"에서 고르세요.
- **날짜는 패널이 실행 중인 머신의 시간대로 나눕니다.** 제공업체가 다른 시간대로 정산하면 주기 첫날과 마지막 날에 몇 시간 분의 차이가 생깁니다.
- **패널 연결이 끊겼거나 재시작한 동안의 트래픽은 나중에 채워집니다.** 다만 호스트가 재부팅하면 마지막 샘플부터 재부팅까지 몇 초는 빠집니다.
- **패널에 연결하기 전에 쓴 트래픽은 측정할 수 없습니다.** "한도 설정"에 제공업체 패널에 표시된 이번 주기 사용량을 입력하면 이번 주기를 그에 맞춥니다. 보정은 현재 주기에만 적용되고 다음 주기에는 사라지며, 과금 방식·인터페이스·초기화일을 바꿔도 지워집니다.

정확한 값은 제공업체 청구서를 기준으로 하세요.

### 업그레이드 후 네트워크 속도가 낮아졌습니다

이제 네트워크 속도도 월 트래픽과 같은 기준으로 업링크 인터페이스만 셉니다. 예전에는 터널과 브리지의 트래픽이 물리 인터페이스에 더해져 같은 트래픽이 두 번 집계되었기 때문에 수치가 높게 나왔습니다. 업그레이드 전에 저장된 기록은 이전 기준 그대로입니다.

### 트래픽 알림이 오지 않습니다

알림 비율(기본 80%, 95%, 100%)에 도달했을 때와 현재 속도라면 한도를 넘을 것으로 예상될 때, "트래픽 알림선 도달"과 "트래픽 한도 초과 예상"을 구독한 알림 채널로 보냅니다. 주기마다 단계별로 한 번만 보냅니다. 기존 알림 채널은 업그레이드 시 두 항목이 자동으로 켜집니다. 꺼 두었다면 "설정 → 알림 및 봇"에서 다시 켜세요. 초과 예상은 주기 안에 하루치 데이터가 모인 뒤부터 판단합니다.

## Hostower 업데이트

### 업데이트한 뒤 페이지에 새 기능이 보이지 않아요

Hostower는 단일 페이지 앱입니다. 서버가 업데이트되어 재시작되면 이미 열려 있는 페이지는 자동으로 다시 연결되고 "설정"에 표시되는 버전 번호도 새것으로 바뀌지만, 페이지 자체의 코드는 여전히 예전 것입니다. `Ctrl+F5`(Mac에서는 `Cmd+Shift+R`)로 한 번 강제 새로 고침하면 됩니다.

### "설정"에 "이 빌드에는 업데이트 소스가 설정되어 있지 않습니다"라고 표시되는 이유는 무엇인가요?

자동 업데이트는 정식 릴리스 버전에서만 동작합니다. 릴리스 공개 키로 서명을 검증해야 하기 때문입니다. 직접 빌드한 버전에는 릴리스 공개 키가 없으므로 바이너리나 이미지를 직접 교체해 업데이트해야 합니다.

### 초기 비밀번호는 어디에 있나요?

데이터 디렉터리의 `initial-password` 파일에 있으며, 로그에는 기록되지 않습니다. Docker로 배포한 경우:

```bash
sudo cat data/initial-password   # compose.yaml이 있는 디렉터리에서 실행
```

로그인한 뒤 되도록 빨리 비밀번호를 바꾸고 Passkey나 인증 코드를 추가하세요. 모든 로그인 수단을 잃었다면 서버에서 `hostower auth reset-password`를 실행합니다.
