# 威胁模型

这个系统等于“所有主机的钥匙”，所以按“直接暴露在公网、且塔台本身可能被攻破”来设计。
本文记录**当前代码**（v0.1.3）里已经有的对策，以及目前没有的。设计见 [design.md](design.md)。

## 资产

- 被管主机上的执行权。
- SSH 凭据。
- 审计记录的完整性。

## 信任边界

```
浏览器 ──► 网关 ──► 安全内核 ──► 执行器 ──► 主机
              ▲          ▲
        认证 / 来源    判级 / 审批 / 审计
```

内核之外的一切（网页、命令行、聊天机器人，以及任何新加的入口）都不可信：它们只能提交请求。

## 已有的对策

| 威胁 | 对策 | 位置 |
| --- | --- | --- |
| 危险命令被执行 | 语法树判级，取最高等级；不认识的按 L1；L3 无人能放行 | `internal/kernel/risk` |
| 判级被绕过（包装、嵌套、管道） | 剥掉 sudo / env / xargs 等包装；递归解析 `sh -c`、`eval`、heredoc；管道进解释器按高危或禁止 | `risk/engine.go`，测试表 |
| 批准之后内容被替换 | 批准绑定到内容摘要；写文件时旧内容变了则作废 | `kernel.Approve`、`kernel.writeFile` |
| AI 或自动化自己批准 | 只有人能批准；L2 只能在网页上批准并要求当场二次验证 | `kernel.Approve` |
| 审计被篡改或删除 | 哈希链 + 数据库触发器 + 文件副本；可离线校验 | `internal/kernel/audit` |
| 口令爆破 | 密码用 Argon2id 存；用户名不对时同样算一次哈希；按来源限速，同一账号连续失败 5 次后开始等待（最多 15 分钟）；成功和失败都入审计 | `internal/auth`、`gateway` |
| 钓鱼 | Passkey 绑定域名，钓不走；密码和动态码可能被实时转发，所以改登录设置时有 Passkey 或动态码就不认密码，批准 L2 只认 Passkey 或动态码、一次验证只能批一次 | `internal/auth`、`gateway` |
| 初始密码泄露 | 首次启动生成 32 位随机密码，只写进数据目录里 0600 的文件，不进日志；改过密码后删除；页面在改掉之前一直提示 | `auth.EnsureOwner` |
| 会话被偷后加一个自己的登录方式 | 改登录方式、密码、动态码、Passkey、单点登录设置之前都要先验证身份；服务端拒绝会把所有者锁在外面的设置 | `gateway/authx.go` |
| 动态码重放 | 记下最后用过的时间步，同一个码（或更早的）不能用第二次；密钥存在凭据存储里（信封加密），只在绑定时显示一次 | `auth.checkTOTP` |
| 会话劫持、跨站请求伪造 | Cookie `HttpOnly` + `SameSite=Strict`（https 下 `Secure`）；写请求校验 Origin 和自定义头；WebSocket 校验 Origin；会话可一键吊销 | `gateway/server.go` |
| 跨站脚本 | 严格的内容安全策略，无内联脚本、无第三方来源；远端内容按纯文本渲染 | `gateway.headers`、前端 |
| 数据库泄露 | 凭据信封加密，主密钥不进数据库；会话令牌只存哈希。没有显式配置时主密钥自动生成在数据目录里：只泄露数据库文件仍然安全，泄露整个数据目录或其备份则不安全，凭据页会提示把它移出去 | `internal/secrets`、`internal/auth` |
| SSH 中间人 | 主机公钥首次信任后固定，不一致则拒绝 | `executor/ssh.go` |
| 注入 Snippet 参数 | 参数有类型和校验；渲染时全部做 shell 转义；渲染结果仍然判级 | `internal/snippet` |
| 不安全的暴露方式 | 启动自检：对外监听而没有 TLS 则拒绝启动；开发模式只能监听本机 | `app.Config.SelfCheck` |
| 资源耗尽 | 请求体、输出、主机数都有上限；批量执行有界并发；慢的事件订阅者丢事件 | `gateway`、`kernel` |

## 目前没有的对策

下面这些对策目前没有，所以在通过外部安全评审之前，**建议只在内网或放在会验证身份的反向代理之后使用**：

- SSH 短期证书：目前塔台保存的是长期私钥（加密存储）。塔台被攻破且主密钥泄露时，攻击者能拿到它们。
- 多用户、角色范围、API 令牌。
- 审计只写本地（数据库和 JSONL 文件副本），没有 syslog、对象存储等外部接收端。
- 软件物料清单；发布签名已有（见“自我更新”），但私钥的保管还比较简单。
- 外部安全评审。

## 交互终端

终端是内核里唯一不逐条判级的路径：塔台看到的只是字节流，分不清哪一段是命令。
所以内核管的是“开终端”这个动作，而不是里面敲了什么：

- 固定按 L2 处理：当场确认并重新验证身份。
- 只有人能开；AI、API 令牌、插件都不行。
- 整段输出录制成文件（asciicast 格式），开始和结束写审计。键盘输入不单独录制，因为它可能含口令。
- “暂停全部执行”和吊销会话都会立刻断开终端；长时间没有操作也会断开。

这意味着 L3 规则在终端里不生效：在终端里敲 `rm -rf /` 会被执行。这是有意的取舍，靠的是事前的高危确认和事后的录像，而不是事中的拦截。

## 文件预览

主机上的文件可能是被人故意构造的（带脚本的 SVG、带 HTML 的 Markdown、恶意的 PDF 或 Office 文档）。预览时：

- 文件以二进制取回，接口按附件、`application/octet-stream` 返回，浏览器不会把它当网页打开；页面用脚本读出字节后自己解析。
- 图片放进 `<img>`（`data:` 地址），SVG 里的脚本不会执行；PDF 用 pdf.js 画到 canvas，不进 iframe、不用浏览器内置阅读器，
  不加载 pdf.js 的脚本沙箱；Markdown 不解析原始 HTML、不加载外部图片；Office 文档只取文字和表格结构，按纯文本显示。
- 内容安全策略没有为此放宽（仍然只允许本站脚本、本站样式、本站和 `data:` 图片，不允许 iframe 和插件）。
- 剩下的风险在解析库本身：pdf.js、react-markdown、fflate 或浏览器的 XML 解析器有漏洞时，构造的文件可能触发它。
  它们都在浏览器里运行，受同源和内容安全策略限制；预览只在用户点开文件时发生。

## 审计的范围

审计分两类：

- **关键操作，永远记录**：登录和登录失败、提交、批准和拒绝、每一次执行和它的结果、打开和结束终端、
  读取和下载文件内容、上传、凭据和主机的增删改、Snippet 的改动、面板和更新设置的改动、暂停与恢复。
- **日常查看，默认不记**：翻目录，以及页面上的只读查询（列容器和镜像、看容器日志、看容器配置、按名字搜文件）。
  这些查询只能是 L0 的只读命令，数量很多（打开一次容器页就是好几条），全记下来会淹没关键操作。

所有者可以在“设置 → 审计”里打开对日常查看的记录；每次开关都会写一条审计，所以事后能看出哪段时间没有记。

### 审计归档

记录太多时可以归档：这是审计记录唯一的删除路径，默认关闭。

| 威胁 | 对策 |
| --- | --- |
| 借“归档”悄悄删掉不想被看到的记录 | 只能按所有者设定的条件归档最老的一段，不能挑着删；归档本身在链里留一条 `audit.archived`；改条件先写审计 |
| 归档文件被改动或替换 | 检查点里存着文件的 SHA-256 和最后一条的哈希，检查点表只追加；`hostower audit verify` 逐个校验文件摘要、文件里的链，以及和检查点、前后文件的衔接 |
| 删了数据库里的记录、却没有可用的归档 | 先写好文件（落盘、改名）并在链里留下记录，最后才删；任何一步失败都不删 |
| 绕过归档直接删数据库 | 触发器只允许删除最新检查点之前的记录；检查点本身不能删改 |
| 归档文件和数据库在同一个目录，一起丢 | 这一点归档不解决：要长期保留，把 `audit-archive/` 和 `audit.jsonl` 转存到别处 |

关着它的代价要清楚：有人拿到了登录会话之后翻过哪些目录、看过哪个容器的日志和配置，审计里查不到。
容器配置里看起来像口令的环境变量在服务端就被遮掉了，日志原文则没有。对这一点在意的部署应该把它打开。

## 指标采样

采样是内核那条路之外的第一类例外（见 AGENTS.md）：它不判级、不审批、不逐次写审计，
因为运行的只有编译进程序的固定脚本，并且内核启动时会确认这些脚本被判为 L0，否则拒绝启动。

- 每台主机一条长连接，主机上循环运行 `executor.StreamProbeCommand`：每 5 秒读一轮 `/proc` 并输出。
  读取全部用 shell 内建命令，不启动进程；每轮只有一次 `sleep`，每分钟一次 `df`。主机上不需要安装任何东西。
- 脚本里没有任何来自清单、页面或主机的内容，也不接受参数；输出只当文本解析，不会被执行。
- “暂停全部执行”会立刻断开所有采样连接，暂停期间也不会重连。
- 容器占用在同一个脚本里直接读 cgroup 文件；读不到时退回每分钟一次的 `docker stats`，同样是固定命令。
- 硬件信息（`executor.HardwareProbeCommand`）在连上主机时读一次、之后每 6 小时一次：`lscpu`、`/proc/cpuinfo`、
  `/sys/class/dmi/id` 里人人可读的厂家和型号文件、`/sys/block` 下的磁盘容量和型号。不读序列号、资产编号这类只有 root 能读的字段，
  也不运行 `dmidecode`，所以内存条型号和频率读不到。

### 增强采集程序

采样脚本每分钟检查主机上的固定位置 `~/.hostower/bin/hostower-agent`，有就运行它（`stream`）。
这是采样这一类例外里唯一会运行“主机上的程序”的地方，所以把边界写清楚：

- 它怎么到主机上：只能通过面板上的安装，那是一个 L1 请求，内容是 Hostower 自带的那份程序（编译进可执行文件里，
  不从网络下载），摘要绑定它的 SHA-256，由人批准。
- 判级引擎只把“这个固定路径 + 参数恰好是 `stream`”判为 L0；换个路径、多一个参数都是 L1。
- 它以 SSH 登录的那个账号运行，没有比这个账号更多的权限；只读 `/proc`、`/sys`、cgroup 和文件系统用量，不监听端口，连接断开就退出。
- 剩下的风险：能写这个账号家目录的人可以把它换成别的程序，之后它会被自动运行。但能写这个家目录的人本来就已经能以这个账号执行任何命令，
  所以这不扩大权限；它影响的是“自动运行”这一点。在意的话不要安装，基础指标完全不依赖它。
- 输出只当文本解析，不会被执行。

## 内置的本机

在 Linux 上直接运行二进制时，清单里默认有一台名为 `local` 的主机：Hostower 自己所在的机器，
通过本机执行器（`executor/local_linux.go`）直接执行，不需要配置 SSH。它和别的主机走同一条路：
判级、审批、审计都不变。它的标签和敏感度可以在页面上改，名字和连接方式是固定的，也不能删除。
这台机器上跑着管理入口本身，建议把它的敏感度设为“高”（默认是“普通”）。

它和 SSH 主机的区别是**没有账号隔离**，这是为了开箱即用做的取舍：

- 命令以运行 Hostower 的账号执行。这个账号读得到数据目录（数据库、审计副本）和主密钥文件，
  所以“能在本机上执行只读命令”就等于“能读到主密钥”。SSH 主机没有这个问题：远端账号读不到 Hostower 的数据。
- 因此不要用 root 运行 Hostower；给它一个专用账号，需要管容器就加入 `docker` 组
  （注意 `docker` 组本身等同 root）。示例见 `deploy/hostower.service`。
- 需要隔离时设置 `HOSTOWER_LOCAL=0` 关掉它，改为新建一个专用账号、用 SSH 连 `127.0.0.1`。
- 默认的容器镜像里没有 shell，本机执行器在容器里不存在；容器部署要管宿主机，用 SSH，或者用下面的宿主机版。

### 宿主机版镜像

`deploy/compose.host.yaml` 用的镜像（`--target host`）设置了 `HOSTOWER_LOCAL=host`：本机执行器先用 `nsenter`
进入宿主机（1 号进程）的挂载、网络等命名空间再执行命令，文件经 `/proc/1/root` 读写。
这样容器部署也有内置的本机，但它放弃的东西比直接运行二进制更多：

- 容器必须是特权的（`privileged: true`）并共用宿主机的进程命名空间（`pid: host`）。默认镜像的加固
  （非 root、去掉全部权限、没有 shell）在这个版本里都不存在。
- 本机上的命令以 **root** 身份在宿主机上执行，没有“专用账号”这一层。Hostower 被攻破等于这台机器被完全控制。
- 进不去宿主机时拒绝启动，而不是带着一台不能用的本机运行。
- 容器自己的环境变量不会带到宿主机上的命令里。

## 自我更新

设置里可以打开自动更新（默认关闭）。它换的是 Hostower 进程自己，不经过执行器，也不碰任何主机，
所以不是内核那条路之外的第三条路：没有任何主机上的命令因为更新而被执行。

- **信任的根是编译进可执行文件的发布公钥**，不是 GitHub，也不是下载通道。新版本必须带着用发布私钥做的签名，
  对不上就什么都不换，并记一条审计。GitHub 账号、发布页或网络被攻破，都发不出能通过验签的更新。
- 签名只证明“这是发布过的文件”，所以还会核对文件自己报出的版本号：必须等于发布页上的版本、并且比当前的新。
  这样拿一份有真签名的旧版本冒充新版本也行不通。
- 新版本放在数据目录的 `update/` 下，进程原地切换过去；容器和镜像都不动。之后每次启动，镜像里的那份会重新验签再接力。
- 切换过去之后没能启动成功的版本，下次启动时会被丢弃，继续用镜像里的版本。
- 只认 `v1.2.3` 这种正式版本；自己编译的、没有配置发布公钥的构建不会自我更新。
- 打开之后，服务端会定期访问发布页（默认是 GitHub），请求里不带任何实例信息。

目前没有的：发布私钥放在发布流程的机密里，没有硬件密钥或多人签名；数据库没有在更新前自动备份，
新版本如果升级了数据库结构，就不能直接退回旧版本。

## 通知

通知让 Hostower 主动往外发请求（Telegram、飞书、Discord、SMTP）。它只读事件、只往外说，不接收任何指令。

| 威胁 | 对策 |
| --- | --- |
| 拿通知功能让服务端去访问内网（SSRF） | Telegram 的地址是写死的；飞书、Discord 的 Webhook 只接受官方域名和固定路径的格式，填别的直接拒绝。邮件服务器可以随便填（自建邮件服务很常见），但只有所有者能配置，且每次修改写审计 |
| 聊天账号变成新的操作入口 | 通知里没有任何可以操作的按钮，只有回到页面的链接；批准、执行仍然要在网页上登录，L2 还要 Passkey 或动态码 |
| 通知内容里的恶意文本（命令、主机返回的错误）去提醒或骚扰别人 | 所有渠道只发纯文本；Discord 关掉提及解析，`@everyone` 不会生效；字段长度有上限 |
| 机密泄漏 | Token、Webhook、密码存在凭据库，接口和列表里只有“有没有设置”；发送失败的错误信息里去掉完整地址（Telegram 的地址里带着 Token） |
| 通知里带出敏感信息 | 只带摘要：请求说明、等级、主机、发起人、失败原因的前几行；不带命令的完整输出、文件内容和凭据引用以外的任何凭据信息 |
| 通知压垮主流程或被刷屏 | 独立队列，满了丢弃；一分钟内去重；每个渠道每分钟最多 20 条 |
| SMTP 明文 | 不加密只允许在不登录的情况下用（通常是本机或内网的中继），要登录就必须 SSL/TLS 或 STARTTLS；证书照常校验 |

目前没有的：通知送达不进审计（避免一条审计触发一条通知再触发一条审计）；飞书、Discord 的发送结果只看 HTTP 状态和返回码，不确认消息真的被看到。

## 聊天入口

所有者可以把 Telegram 账号绑定到 Hostower，私聊机器人查状态、提交命令、紧急暂停。它是网关的一个入口（`Entry: "chat"`），不是旁路：
发送者核对通过之后，网关构造 Actor，之后照常走 `Submit*` → 判级 → 审批。

| 威胁 | 对策 |
| --- | --- |
| 别人冒充所有者给机器人发命令 | 只认私聊；发送者的 Telegram 用户编号由 Telegram 服务器填写，必须等于绑定的那个；其他人的消息一律不回应，也不暴露机器人的用途 |
| 绑定被劫持（把攻击者的账号绑上） | 配对码只能由已登录的所有者在网页上生成；8 位、5 分钟有效、只能用一次、输错 5 次作废，输错还会写审计并发“登录失败”通知 |
| 所有者的 Telegram 账号被盗（手机丢失、SIM 卡被劫持、会话被盗） | 聊天里的身份不能批准任何请求，不能恢复执行、开终端、改设置、改凭据；能造成的最大影响是提交请求（L1 以上仍要在网页上用 Passkey 批准）、执行 L0 的只读命令、暂停全部执行。绑定有有效期，网页上可以随时解除，“吊销所有会话”也会一起解除 |
| 机器人令牌泄漏 | 令牌只能冒充机器人，不能冒充所有者给机器人发消息；令牌存在凭据库，聊天入口拿不到它本身 |
| 伪造回调 | 不开放任何回调接口：Hostower 主动长轮询 Telegram |
| 积压或重放的旧消息 | 启动时跳过积压的消息；超过 2 分钟的消息不处理 |
| 用命令刷屏、刷审计 | 每分钟最多 20 条命令，超出的只提醒一次 |
| 命令和输出经过 Telegram 的服务器 | 机器人对话不是端到端加密的：只读命令的输出会经过 Telegram。输出先过一遍凭据遮蔽，并截断到 3 KB 左右；不想让输出离开 Hostower 就不要打开这个功能 |

限制：聊天入口只支持 Telegram；任何等级都不能在聊天里批准（有意为之：聊天账号一旦被盗，不应该能放行变更）。

## 单点登录（OIDC）

| 威胁 | 对策 |
| --- | --- |
| 身份提供方那边谁都能注册，冒充所有者 | 只有“允许的账号”能进：邮箱必须是提供方验证过的（`email_verified`），或者按 `sub` 精确匹配 |
| 登录流程被劫持（CSRF、授权码被截获、重放） | state 只能用一次，并且要和只给回调路径用的 Cookie 对上；PKCE；nonce；身份令牌的签名、签发方、受众、有效期都校验 |
| 身份提供方或账号被攻破 | OIDC 只替代登录：高危操作（L2）仍要当场用 Passkey 或动态码确认，开终端同样；每次登录写审计，登录失败会发通知 |
| 客户端密钥泄露 | 存在凭据存储里，只写不读 |
| 拿配置功能访问内网 | 签发方地址必须是 https（只有本机地址允许 http），只有所有者能改，每次修改写审计 |

## 测速

测速是一条固定的命令，从主机向 speed.cloudflare.com 下载、上传一段数据。它照常走判级（L1）和审批；
多台主机一起测是一个请求、一次批准。主要的风险是流量：页面上会提示每台主机大约消耗多少流量。
结果只从“和我们生成的测速命令完全一致”的那些执行里解析。路由追踪的目标只接受 IP 或域名（不含空格和引号），放在单引号里；目标变了命令就变了，批准照样绑定实际命令。输出里的 IP、节点名、路由按纯文本显示，trace 只取几种短字段。

## 已知的判级局限

- 判级是静态的：它看不到脚本文件的内容（`bash deploy.sh` 是 L1，由批准人负责看）。
- 读内容的命令带运行时才确定的参数时按 L1，而不是 L0，因为无法保证它不读敏感文件。
- 数据库客户端的语句只做关键字匹配；复杂的破坏性语句可能只被判为 L1。
- 发现被低估的命令请按 [SECURITY.md](../SECURITY.md) 报告，我们会把它加进测试表。
