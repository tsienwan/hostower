## ホストの接続

### なぜ SSH 認証情報に root を使えないのですか？

Hostower は「すべてのホストの鍵」に相当するため、ホスト側にも Hostower 自身では開けない扉がもう 1 つ必要です。

1. **パネルが侵害されたときの被害を抑える**：データベースとマスターキーが漏えいすると、攻撃者は Hostower が保存している秘密鍵を手に入れられます。root の秘密鍵はホスト全体をそのまま乗っ取れることを意味しますが、制限付きのアカウントなら sudo で許可されたことしかできません。
2. **判定は完璧にはなりえない**：判定エンジンはシェルを解析する必要があり、想定外の回避方法が常に存在しうるからです。sudo の制限はホストのシステムが強制するもので、独立した第二の安全装置になります。
3. **対話ターミナルはコマンドごとに判定しない**：ターミナルを開くには L2 の承認が必要で、全体が録画されますが、中で入力したコマンドは 1 つずつ判定されません。root でログインしていれば、承認された時点で何でもできてしまいます。
4. **運用上の慣習**：多くのシステムはデフォルトで root の SSH ログインを禁止しています。専用アカウントでログインすれば、ホストの `auth.log` や sudo のログで、どの操作が Hostower によるものかを区別できます。

これは厳格な制限です。ユーザー名に `root` を入力すると、その場で拒否されます。

### Hostower 用の専用アカウントはどう作りますか？

管理対象のホストで、root として次を実行します。

```bash
useradd -m -s /bin/bash hostower
mkdir -p /home/hostower/.ssh
echo 'ssh-ed25519 AAAA…（公開鍵）' >> /home/hostower/.ssh/authorized_keys
chown -R hostower:hostower /home/hostower/.ssh
chmod 700 /home/hostower/.ssh
chmod 600 /home/hostower/.ssh/authorized_keys
```

続いて次の節に従って sudo を設定し、Hostower の **認証情報** で SSH 認証情報を追加します。ユーザー名には `hostower` を、秘密鍵には上記の公開鍵と対になるもの（`-----BEGIN` から `-----END` までの全体）を入力します。

### root はすでに鍵でログインできます。新しいアカウントにも鍵を設定する必要がありますか？

必要です。公開鍵はアカウントごとに置かれます。各アカウントは自分のホームディレクトリにある `~/.ssh/authorized_keys` の公開鍵しか認めず、`/root/.ssh/authorized_keys` は root にしか効きません。

方法は 2 つあります。

- **推奨：Hostower 用に別の鍵を生成する**。root は元の鍵を使い続け、その秘密鍵は自分の手元だけに置いて Hostower には渡しません。

  ```bash
  ssh-keygen -t ed25519 -f hostower_key -N ""
  ```

  `hostower_key.pub` の内容を hostower アカウントの `authorized_keys` に書き込み、`hostower_key` の内容を Hostower の認証情報に入力します。
- **手軽：root の公開鍵をコピーする**。

  ```bash
  cp /root/.ssh/authorized_keys /home/hostower/.ssh/
  ```

  その代わり、同じ秘密鍵で hostower にも root にもログインできるため、Hostower から漏えいすれば root が漏えいしたのと同じことになります。この方法を取る場合は、`/etc/ssh/sshd_config` で `PermitRootLogin no` を設定し、sshd を再起動することをおすすめします。変更する前に、hostower でログインでき、`sudo -i` で root に切り替えられることを確認してください。そうしないと自分自身を締め出してしまうおそれがあります。

### 秘密鍵に対応する公開鍵がどれか思い出せません

秘密鍵を保存しているコンピューターで公開鍵を書き出します。

```bash
ssh-keygen -y -f 秘密鍵ファイル
```

### エラー `ssh: unable to authenticate, attempted methods [none publickey]`

これはネットワークの接続はできているものの、ホストがこの秘密鍵を受け付けていないことを意味します。よくある順に確認してください。

1. **公開鍵がこのアカウントの `authorized_keys` に入っていない**。`sudo cat /home/hostower/.ssh/authorized_keys` で確認します。ファイルが存在しないと表示されたら、まだ入れていません。
2. **権限が緩すぎる**：sshd はこうした公開鍵を黙って無視します。`.ssh` ディレクトリは 700、`authorized_keys` は 600 にし、所有者はどちらもそのアカウントにする必要があります。
3. **ユーザー名が違う**：認証情報に入力したユーザー名は、公開鍵を置いたアカウントと一致している必要があります。
4. **秘密鍵の貼り付けが不完全**：先頭行や末尾行が欠けている、または改行が失われている。

ご自身のコンピューターで確認してみてください。

```bash
ssh -i 秘密鍵ファイル -o IdentitiesOnly=yes hostower@192.0.2.10
```

これでもログインできない場合は、ホスト上の sshd のログを見ます。

```bash
sudo journalctl -u ssh -u sshd -n 30 --no-pager
```

ログに `bad ownership or modes` があれば権限の問題、`Invalid user` があればユーザー名の誤りです。自分ではログインできるのに Hostower ではログインできない場合は、**認証情報** で秘密鍵をもう一度貼り付けてください。

設定が済んだら、ほかに何もする必要はありません。Hostower が自動で再接続します。

### エラー「ホストの公開鍵が初回接続時と一致しません」

Hostower は初めてホストに接続したときにその公開鍵を記録し、以後一致しなければ接続を拒否します。これは誰かが途中でなりすましている可能性もあれば、ホストの OS が再インストールされた可能性もあります。再インストールであることを確認したら、Hostower を実行しているマシンで古い記録を消去します。

```bash
hostower hostkey forget web-1
```

## sudo

### アカウントに sudo を設定すべきですか？どう設定しますか？

パッケージのインストール、Docker のインストール、ファイアウォールの変更などの操作には root が必要です。root ではないアカウントは `sudo -n`（パスワードなし。パスワードの入力待ちで止まることはありません）を使います。設定方法は 2 つあります。

**方法 1：すべてのコマンドをパスワードなしで実行（最も手軽）**

```bash
echo 'hostower ALL=(ALL) NOPASSWD: ALL' > /etc/sudoers.d/hostower
chmod 440 /etc/sudoers.d/hostower
visudo -c
```

`visudo -c` は必ず実行し、`parsed OK` と表示されれば構文に誤りはありません。sudoers の書き方を誤ると、sudo 全体が使えなくなることがあります。

こう設定すると、このアカウントは権限の面で root に近くなります。保護は Hostower 自身によるものです。すべての変更は判定され、あなたの承認が必要で、監査に記録されます。root で直接ログインする場合と比べて、2 つの利点は残ります。root の SSH ログインを禁止できること、そしてどの操作が Hostower からのものかをログで区別できることです。

**方法 2：一部のコマンドだけを許可（許可リスト）**

Hostower に少数の作業だけをさせたい場合に適しています。たとえば：

```
hostower ALL=(root) NOPASSWD: /usr/bin/systemctl, /usr/bin/journalctl
```

注意点として、`env`、`tee`、`docker`、`sh` のようなコマンドを許可リストに入れると、それらを介して任意のコマンドを実行したり任意のファイルに書き込んだりできるため、効果は方法 1 と同じになります。そして **Docker をインストール** のような機能はまさにこれらのコマンドを使うため、方法 1 と組み合わせてしか使えません。

**有効になったか確認する**：

```bash
su - hostower -c 'sudo -n true && echo ok'
```

### 古いシステムで `you must have a tty` と表示される

CentOS 7 のような古いシステムでは、sudoers に `Defaults requiretty` が含まれていることがあります。このアカウントについてだけ無効にする必要があります。

```bash
echo 'Defaults:hostower !requiretty' >> /etc/sudoers.d/hostower
visudo -c
```

## Docker とコンテナアプリ

### アプリのインストール時に「このホストには Docker Compose v2 がありません」と表示される

ホストに Docker がインストールされていないか、Docker はあっても `docker compose` プラグインがありません。現在は、アプリのインストールダイアログと **コンテナ** ページが先に確認を行い、足りない場合はその旨を表示して **Docker をインストール** ボタンを出します。

- ボタンを押すとリクエスト（L1）が作成されます。承認時には、このホスト向けに組み立てられたすべてのコマンドを確認でき、承認して初めて実行されます。
- Debian、Ubuntu、Raspbian、CentOS 系（Rocky、AlmaLinux、RHEL）、Fedora は Docker 公式のリポジトリからインストールし、Alpine、Arch、openSUSE はシステム標準のリポジトリを使います。「スクリプトをダウンロードしてそのまま実行する」方式（`curl … | sh`）は使いません。
- Docker はすでにあり Compose だけが足りない場合は、Compose プラグインだけをインストールします。
- アカウントが root であるか、パスワードなしで sudo できる（前の節を参照）必要があります。そうでない場合、ボタンは表示されません。
- システムを識別できない場合は、Docker 公式のドキュメントに従って手動でインストールしてください。

### Docker をインストールした後、コンテナページに `permission denied … docker.sock` と表示される

ログインアカウントが `docker` グループに入っていません。Hostower は自分をこのグループに追加しません。docker グループに入ることは root 権限を得ることに等しいため、この手順はホスト上で人が行うしかありません。

1. ホスト上で root として次を実行します（コンテナページからこのコマンドを直接コピーできます）。

   ```bash
   usermod -aG docker hostower
   ```

2. コンテナページに戻り、**再接続** をクリックします。

アカウントを新しいグループに追加した後は、ログインし直さないと反映されません。**再接続** は Hostower からこのホストへの接続を切断し、もう一度ログインし直すもので、Hostower を再起動する必要はありません。注意：切断時に、このホスト上で実行中のコマンドは中断されます。

ホストモードの `local` ホストは例外です。Hostower プロセス自身の権限を使うため、反映させるには Hostower を再起動する必要があります。

### なぜコンテナ名が `3x-ui-3x-ui-1` のように重複した名前になるのですか？

これは Docker Compose のデフォルトの命名規則（プロジェクト名-サービス名-連番）で、旧バージョンではこうなっていました。現在は、サービスが 1 つだけのアプリではコンテナ名がインスタンス名になり、サービスが複数あるアプリではコンテナ名が「インスタンス名-サービス名」になります。

すでにインストール済みのアプリは、**インストール済み** で一度設定を変更するか更新すれば、コンテナが新しい名前に置き換わります。データディレクトリには影響しません。ホスト上に同じ名前で Hostower がインストールしたものではないコンテナがすでにある場合は、デプロイ時に名前の衝突が報告されるので、先にそのコンテナを処理してください。

### アプリをインストールしました。どこから開けますか？初期アカウントとパスワードは何ですか？

**アプリ → インストール済み** で、その行のロケットアイコン（**スタートガイド**）をクリックします。アクセス先アドレス（そのままクリックして開けます）、初期アカウントの説明、次に行う手順が載っています。インストールのリクエストが正常に実行された後は、リクエストの詳細ページにも同じ入口があります。

- 初期パスワードをインストール時に決められるアプリ（OpenList の admin パスワード、LiteLLM のマスターキー、データベースのパスワード）では、インストール時に選んだアプリシークレットがそのパスワードです。
- 初回アクセス時に自分で管理者を作成するアプリ（Uptime Kuma、Portainer、Open WebUI、New API、n8n）には初期アカウントがありません。インストール後はできるだけ早く開いて登録を済ませてください。
- 3x-ui の初期ユーザー名とパスワードは初回起動時にランダムに生成され、コンテナログに一度だけ出力されます。スタートガイドで **初期のユーザー名とパスワードを読み出す** をクリックすると、パネルが 1 回の読み取り専用クエリでその行を読み出します。コンテナを再作成した後はログに残っていないので、その場合はガイドに記載のコマンドを使ってホストのターミナルで設定し直してください。

アドレスが開けないときは、まず待ち受けアドレスが `127.0.0.1` になっていないか確認します（ホスト自身からしかアクセスできません。リバースプロキシを設定するか、**設定を変更** で `0.0.0.0` に変えてください）。次に、ホストのファイアウォールとクラウド事業者のセキュリティグループでそのポートが許可されているか確認します。

### **パネルを開く** で開くアドレスが違う、またはアプリが `127.0.0.1` だけで待ち受けている

Web パネルのあるアプリ（OpenList、3x-ui、Uptime Kuma、Portainer、LiteLLM、Open WebUI、New API、n8n）には、**インストール済み** の行に **パネルを開く** ボタンがあります。アドレスは既定でインスタンスの現在の待ち受けアドレスとポートから組み立てるので、**設定を変更** で変えればボタンも追従します。そのホストに Hostower で追加したサイトがこのアプリのポートへリバースプロキシしていて、パネルアドレスを設定していない場合、ボタンはサイトのアドレスを開きます。合わないときは、隣のリンクアイコンから **パネルアドレス** を設定します（変更できるのはオーナーだけ。Hostower にだけ保存され、ホストは変更せず、変更はすべて監査ログに残ります）。

- **ホストに直接**：ポートやパスをアプリ自身の画面で変えた場合（たとえば 3x-ui の「パネル設定」でポートとパネルパスを変えた場合）は Hostower から見えないので、ここに新しいポートとパスを入力します。
- **完全なアドレス**：アプリの前にリバースプロキシがある、ドメインでアクセスする、または `127.0.0.1` だけで待ち受けている場合は、ブラウザで開くアドレス（例：`https://panel.example.com/xui/`）を入力します。ネットワーク画面にこのポートへリバースプロキシしているサイトがあれば一覧に出るので、クリックで入力できます。
- **SSH トンネル経由**：ポートを外部に公開したくない場合は、画面に表示される `ssh -N -L ローカルポート:127.0.0.1:アプリのポート ユーザー@ホスト` を自分のコンピューターで実行すると、ボタンは `http://localhost:ローカルポート/パス` を開きます。

パネルアドレスにはユーザー名、パスワード、`?` や `#` 以降のパラメーターを含められないので、ボタンのリンクに認証情報が入ることはありません。

### 「環境」ページの「制限あり」「接続不可」とは何ですか？

ホストページの **環境** と **アプリ → 環境** は、このホストから読み取り専用のリクエストをまとめて送り、各サービスがどう応答するかを見ます。

- **AI サービスの地域判定とリスク管理**：ChatGPT、Claude、Google（YouTube が判定した地域を使います）がこのホストをどの地域と判定しているか、その地域がよくあるサービス対象に入っているか。ChatGPT の Web 版が人間確認を求めていないか、Google 検索が異常トラフィックと判定していないか。IP データベースの位置と AI サービスが判定した地域が一致しているか（一致しないと、非対応地域として扱われることがよくあります）。
- **大規模モデルの API**（OpenAI、Anthropic、Google Gemini、xAI、DeepSeek）：キーを付けずにリクエストします。「キーがない」と応答すれば**利用可能**で、キーを設定すれば呼び出せます。出口のある国や地域を理由に拒否されれば**制限あり**です。別の地域のホストに替えるか、LiteLLM や New API のようなゲートウェイ経由で転送してください。
- **Web サイトとストリーミング**（Google、YouTube、Netflix、Disney+、TikTok、Facebook、X、ChatGPT の Web 版など）：通常どおり開ければ**利用可能**、拒否されたり「お住まいの地域ではサービスを提供していません」というページに誘導されたりすれば**制限あり**です。YouTube と Netflix はどの地域になるかも表示します。Netflix はオリジナルではない作品で判定しており、「オリジナル作品のみ視聴できます」は、その地域のライブラリがこのアドレスには開放されていないことを意味します。
- **接続不可**：8 秒以内に接続できませんでした。ネットワークで遮断されているか、ホストに `curl` がない可能性があります。
- **不明**：接続はできましたが、応答が上のどれでもなく、判断できません。

ここではサービスがどう応答するかだけを見ており、どのアカウントにもログインしていません。各社の Web 版やサブスクリプションでのログインには、それぞれ別の地域ルールやリスク管理ルールがあり、API が利用可能でも、サイトが開けても、アカウントが使えるとは限りません。同じページには、ホストにインストールされている AI コマンドラインツール（Claude Code、Codex CLI、Gemini CLI など）と実行環境も表示されます。バージョンはインストールディレクトリから読み取っており、これらのプログラムを実行することはありません。

### 「送信元 IP」の種類とリスクスコアとは何ですか？正確ですか？

Web サイトから見えるのはホストの出口アドレスです。その種類や、悪用の記録があるかどうかによって、制限されるか、人間であることの確認を頻繁に求められるかが変わります。

- **種類**：データセンター、家庭用回線、法人専用線、モバイル回線など。VPS はたいていデータセンターのアドレスで、ストリーミングではオリジナル作品しか見られないことが多く、AI サービスのサブスクリプションでのログインもリスク管理に引っかかりやすくなります。
- **プロキシ判定**：データベースがそのアドレスをプロキシまたは VPN の出口として登録しているかどうか。
- **リスクスコア**：0 から 100 で、高いほどこのアドレスやその属するネットワーク帯域に悪用の記録が多いことを示します。33 未満は低、66 を超えると高です。
- このほか、運営者（ASN）、位置、Cloudflare WARP を経由しているかも表示します。
- IPv4 と IPv6 は別々に調べ、別々に表示します。IPv6 があるホストでは多くの Web サイトが IPv6 を優先し、二つの出口の帰属や評判が異なることがあります。

これらの情報は、ホスト自身が公開の IP データベース（proxycheck.io）に自分の出口アドレスを問い合わせて得たもので、あくまで参考です。データベースによって結論が異なることがあり、各サイトのリスク管理もこれだけで決まるわけではありません。取得できなかったときは「見つかりませんでした」と表示され、ほかの検出には影響しません。

### 「Agent コラボレーション」とは何ですか？アシスタントがホストを勝手に変更しませんか？

「Agent コラボレーション」ページでは、同じタスク（たとえば「nginx の設定と最近のエラーログを確認する」）を複数のホストの Claude Code、Codex CLI、Gemini CLI に割り当てられます。各ホストのアシスタントは自分のホスト上でだけ作業します。実行が終わったら各ホストの結論を並べて比較し、「まとめ」をクリックして、そのうちの一台のアシスタントに比較・要約させることができます。

- タスクの割り当ても、まとめも申請です。まず各ホストで実行されるコマンドとリスクレベルが表示され、承認されてから実行されます。監査にも通常どおり記録されます。
- 既定は読み取り専用です。アシスタントは見るだけで変更はできず、コマンドを実行させようとすると拒否されます。「作業ディレクトリ内のファイルの変更を許可」をオンにしても、許可されるのは作業ディレクトリ内の変更だけです（Claude Code の acceptEdits、Codex の workspace-write サンドボックス、Gemini CLI の auto_edit）。
- ページには、権限確認やサンドボックスをスキップするスイッチはありません。こうしたコマンドを手で入力すると（たとえば `--dangerously-skip-permissions`、`--yolo`）、高リスク（L2）と判定されます。
- アシスタントは、先にアプリカタログでインストールして設定（API キーまたはサブスクリプションでのログイン）しておく必要があります。入っていないホストがあれば知らせます。

ページ上部のコラボレーション図には、タワーがどのホストに何を送っているか（色で Agent タスク、ファイル配布、アプリのインストール、その他のコマンドを区別）、どのアシスタントが思考中か、アシスタントがどの LiteLLM / New API 経由でモデルを呼び出しているかがリアルタイムで表示されます。システムで「視差効果を減らす」（動きを減らす）設定がオンのときは、図のアニメーションが止まります。

### Claude Code や Codex を MCP で Hostower につなぐには？AI が自分で承認することはありますか？

1. 「設定 → セキュリティ → MCP 接続」でトークンを発行します（アシスタントごとに 1 つ。名前はリクエストと監査に表示されます）。トークンは一度しか表示されないので、先に保存してください。
2. アシスタントに設定します。設定ページにアクセス先が入った例があります。
   - Claude Code：`claude mcp add --transport http hostower https://hostower.example.com/mcp --header "Authorization: Bearer <トークン>"`
   - Codex：`~/.codex/config.toml` に次を追加し、
     ```toml
     [mcp_servers.hostower]
     url = "https://hostower.example.com/mcp"
     bearer_token_env_var = "HOSTOWER_MCP_TOKEN"
     ```

     Codex を起動する前にトークンを環境変数 `HOSTOWER_MCP_TOKEN` に設定します。
3. あとはアシスタントに「web-1 のディスクを見て」「web-1 の nginx を再起動して」と頼むだけです。

アシスタントが送信したコマンドは通常どおり判定されます。読み取り専用（L0）はすぐに実行され、結果がアシスタントに返ります。それ以外はリクエストになり「承認」であなたの承認を待ち、アシスタントは `get_request` で結果を待ちます。L3 は常に拒否されます。アシスタントには承認、ターミナルを開く、ファイルの読み書き、設定変更のツールがなく、他の人が送信したリクエストも見えません。リクエストの詳細と監査では、送信者はトークン名、入口は `mcp` と記録されます。

- アシスタントは Hostower のアクセス先に届く場所で動かしてください。パネルがローカルや社内ネットワークからしか開けない場合、アシスタントもその中で動かす必要があります。
- アクセス先の証明書はアシスタントが信頼できるものである必要があります。ブラウザで警告を無視して開いた自己署名証明書（Caddy の `tls internal` や IP だけに発行された証明書など）はアシスタントに拒否され、接続や初期化の失敗として現れます。アクセス先にドメインを割り当てて正式な証明書を使う（Caddy はドメインなら自動で取得します）か、SSH トンネルで Hostower の待ち受けポートを手元に転送し（例：`ssh -N -L 9443:127.0.0.1:9443 <ユーザー>@<サーバー>`）、アシスタントを `http://127.0.0.1:9443/mcp` に接続してください。
- Codex はトークンの環境変数を起動時にしか読みません。デスクトップ版では `HOSTOWER_MCP_TOKEN` をユーザー環境変数として設定し、Codex を完全に終了してから開き直してください。特定のターミナルで一時的に設定した変数は読まれません。
- 使わなくなったら同じ場所で失効させてください。「セキュリティ」の「全セッションを失効」でもすべての MCP トークンが失効します。
- 読み取り専用コマンドの出力は AI サービス事業者を経由します（認証情報らしい内容は先に伏せられます）。それが望ましくなければトークンを発行しないでください。トークンが漏れた場合の影響は[脅威モデル](threat-model.md#mcp-入口)（中国語）を参照してください。

### 各 AI ツールが使ったトークン量を集計するにはどうすればよいですか？

LiteLLM か New API をインストールし（アプリカタログの **AI ツール** にあります）、Claude Code、Codex CLI などのツールの API アドレスをすべてそこに向け、ツールごと、または人ごとに個別のキーを発行します。キーごと、モデルごとの呼び出し回数、トークン使用量、費用は、ゲートウェイ自身の管理画面で確認できます。Hostower 自体はモデルへのリクエストを中継も記録もしません。

### 同じファイルを複数のホストに送るには？複数のホストにあるログを集めるには？

左側の **ファイル同期** を使います。

- **ホストへ配布**：ファイルをドラッグして入れ（一度に最大 20 個）、宛先ディレクトリを入力し、ホストを選びます。ファイルごとに 1 件のリクエストになり、各ホストのどこに書き込むかとリスクレベルをまず確認でき、承認されてから書き込みます。ディレクトリが存在しなければ自動的に作成され、同名のファイルは上書きされます。システムディレクトリへの書き込みには、ログインアカウントに権限が必要です。`/etc/ssh` のような機密性の高いパスへの書き込みは高リスクと判定されます。
- **ホストから収集**：ディレクトリとファイル名のパターン（たとえば `*.log`。`*` は任意の文字列、`?` は 1 文字を表します）を入力し、ホストと何階層下まで探すかを選びます。まず **検索** をクリックしてどんなファイルがあるかを確認し、それから **圧縮ファイルをダウンロード** をクリックします。圧縮ファイルの中には「ホスト名/ファイルパス」の形で格納されます。

収集の制限：ホストごとに最大 200 ファイル、1 ファイルあたり 100 MB まで、1 回の合計は 1 GB までです。読み取れないファイル（秘密鍵、認証情報ファイル、またはログインアカウントに権限がないもの）と上限を超えたものは、圧縮ファイル内の「_跳过的文件.txt」（スキップされたファイル）に記録されます。検索は読み取り専用クエリです。ダウンロードしたファイルは 1 つずつ監査に記録されます。

### バージョンタグを固定したイメージ（たとえば `v3.9.0`）はどう更新しますか？

コンテナページはイメージレジストリのタグ一覧を読み取ります。

- 同じメジャーバージョン内に新しいバージョンがある場合は **新しいバージョン vX** と表示され、更新すると新しいタグに切り替え、元の設定のままコンテナを再作成します。
- メジャーバージョンをまたぐ新しいバージョンは通知するだけで、自動では切り替えません。メジャーアップグレードには互換性のない変更が含まれる可能性があるため、まず更新内容の説明を確認してください。

## サイト、証明書と Fail2ban

### Caddy と Nginx のどちらを選ぶ？

ホスト詳細の「ネットワーク」ページでどちらもワンクリックでインストールでき（システムのリポジトリから）、リバースプロキシ、静的ディレクトリ、リダイレクトの 3 種類のサイトを作れます。

- **Caddy**：HTTPS 証明書を自動で取得・更新するので、いちばん手間がかかりません。特に理由がなければこちら。
- **Nginx**：Nginx に慣れている、またはホストにすでに Nginx の設定がある場合に。証明書は Let's Encrypt で自動取得するか（Hostower が certbot も入れ、certbot が定期的に更新します）、ホスト上の既存の証明書のパスを指定します。

どちらも 80 と 443 番ポートを使うため、Hostower は 1 台に 1 つだけインストールします。管理するのは自分で書いたファイル（`/etc/caddy/sites.d/`、`/etc/nginx/conf.d/hostower-*.conf`）だけで、ホストにもとからある設定には触れません。

### Let's Encrypt の証明書取得に失敗した

失敗した場合、サイトはひとまず HTTP で公開され、ほかのサイトには影響しません。よくある原因：

- ドメインがまだこのホストを向いていない（または DNS の変更が反映されていない）。
- 外部から 80 番ポートに届かない。ホストのファイアウォールとクラウド事業者のセキュリティグループの両方で 80 と 443 を許可してください。
- 80 番ポートを別のプログラムが使っている。
- 同じドメインで短時間に何度も申請し、Let's Encrypt の上限（同じドメインの組み合わせで週 5 枚まで）に達した。

原因を取り除いたら、サイトを取り下げてから追加し直してください。

### サイトのカードに「Caddy · 停止中」と表示される

インストール済みでもサービスが動いていない間は、このホストのサイトはどれも開けず、証明書も取得されません。横の「Caddy を起動」を押してください（Nginx も同じです）。承認後に実行されます。サイトの追加や取り下げのときも、サービスが動いていなければあわせて起動します。

起動に失敗した場合は、リクエストの出力にサービスの直近のログが含まれます。いちばん多い原因は、80 か 443 番ポートを別のプログラム（自分で入れた Caddy、Nginx、コンテナなど）が使っていることです。ポートを使っているプログラムを止めてから、もう一度起動してください。

### 443 番ポートを 3x-ui（Xray）が使っている

同じポートを 2 つのプログラムで待ち受けることはできません。Xray のインバウンドを別のポートに移すか、サイトのアドレスをポート付き（例：`app.example.com:8443`）にしてください。後者の場合、Nginx は既存の証明書しか使えませんが、Caddy は引き続き自動で取得できます。

### 回線の良いホストを入口にして、別のホストのサービスにアクセスしたい

たとえば A は回線が良く、B は容量が大きいので、ブラウザーは A に接続し、A から B のアプリへ転送したい場合：

1. 両方のホストの **ネットワーク** タブで **Tailscale** をインストールし、**ネットワークに参加** します（同じ Tailscale アカウント）。ブラウザーでログインすることも、認証キーをアプリシークレットとして保存してから選ぶこともできます。キーはコマンドや監査ログには現れません。参加すると各ホストに `100.x` の内部アドレスが付きます。
2. A の **ネットワーク** タブでサイトを追加し、種類はリバースプロキシ、**転送先** に B の Tailscale アドレスを選びます（B のネットワークタブを一度開いていれば一覧に出ます。出ない場合は **その他のアドレス** を選んで入力します）。ポートには B のアプリのポートを入力します。

これで A から B までの区間は暗号化されたトンネルを通り、B のポートをインターネットに公開する必要がなくなります。注意点は 3 つ：B のアプリは `127.0.0.1` だけで待ち受けていてはいけません。アップロードもダウンロードも A の通信量に数えられます。Tailscale のインストール、参加、設定変更、切断はいずれも高リスク操作で、承認時に再認証が必要です。

Tailscale を使わずに B のグローバルアドレスを直接入力することもできますが、その区間は平文の HTTP になるため、B のポートは A の IP だけに許可してください。

### Fail2ban に自分や Hostower がブロックされない？

許可リストには常にループバックアドレスと Hostower がこのホストに接続する元のアドレスが入っており、Hostower は鍵でログインするので失敗の記録も残しません。自分のグローバル IP が変わる場合は、よく使うネットワークを許可リストに追加してください。

それでもブロックされたら、「ネットワーク」ページでその IP の横のブロック解除を押すか、別のアドレスやクラウド事業者のコンソールからログインして次を実行します：

```bash
sudo fail2ban-client set sshd unbanip 203.0.113.7
```

Fail2ban はファイアウォールのルールを変更するため、インストール、設定変更、ブロック解除は高リスク操作（L2）です。承認は Web 上でのみ行え、承認時に本人確認が必要です。

## 拡張コレクター

### 拡張コレクターをインストールした後、ページに反映されるまでどのくらいかかりますか？

承認されて実行に成功すると、Hostower はすぐにこのホストのサンプリングを再接続するので、通常は数秒以内に **拡張コレクター &lt;バージョン&gt;** とプロセスランキングが表示されます。待っている間、ボタンには **承認待ち**、**インストール中…**、**収集方式を切り替え中…** が順に表示され、重複して送信されないようになっています。アンインストールも同様です。

## 転送量の上限

### パネルの月間転送量が事業者のパネルと合わない

ホストページの「転送量」カードと概要の「転送量ランキング」の数値は、各インターフェースの累積カウンターから次のルールで数えています。

- **出口インターフェースだけを数えます。** WireGuard・OpenVPN・Tailscale などのトンネル、`br0`・`vmbr0` などのブリッジ、`eth0.100` などの VLAN サブインターフェース、ボンディングのメンバーは同じ通信なので二重に数えません。`lo`・`docker0`・`veth…` などの仮想インターフェースも含みません。特定のインターフェースだけで課金したい場合は「上限を設定」の「集計するインターフェース」で選んでください。
- **日付はパネルを動かしているマシンのタイムゾーンで区切ります。** 事業者が別のタイムゾーンで締めている場合、期初・期末の日は数時間分ずれます。
- **パネルの切断中・再起動中の通信は後から補完されます。** ただしホストが再起動したときは、最後のサンプルから再起動までの数秒が漏れます。
- **パネル接続前に使った分は測れません。** 「上限を設定」で事業者のパネルに表示された今期の使用量を入れると、今期はそれに合わせます。補正は今の期間だけ有効で、次の期間には消えます。課金方式・インターフェース・リセット日を変えた場合も消えます。

正確な値は事業者の請求を確認してください。

### アップグレード後にネットワーク速度が下がった

ネットワーク速度も月間転送量と同じルールになり、出口インターフェースだけを数えます。以前はトンネルやブリッジの通信が物理インターフェースの分に重なり、同じ通信を二重に数えていたため、数値が高めでした。アップグレード前に保存された履歴は以前のルールのままです。

### 転送量の通知が届かない

通知パーセント（既定は 80%・95%・100%）に達したときと、今の速度だと上限を超える見込みのときに、「転送量が通知ラインに到達」「転送量の上限超過の見込み」を購読している通知チャネルへ送ります。期間ごと・段階ごとに 1 回だけです。既存の通知チャネルはアップグレード時に両方とも自動でオンになります。オフにしていた場合は「設定 → 通知とボット」で再度オンにしてください。超過の見込みは、期間内に丸一日分のデータがたまってから判断します。

## リソースのアラート

### ディスク・メモリ・CPU のアラートはいつ送られますか？

Hostower はすでに集めているサンプルで判断し、ホスト上で追加のコマンドは実行しません。

- **ディスク**：いずれかのマウントポイントの使用率が 90% を超えた状態が 5 分続いたとき
- **メモリ**：使用率が 90% を超えた状態が 5 分続いたとき（バッファとキャッシュは使用中に含めません）
- **CPU**：使用率が 90% を超えた状態が 10 分続いたとき

途中で一度でも 90% を下回ると、計測はやり直しになります。アラートを送ったあとは、使用率が戻って（ディスクは 85% 未満、メモリと CPU は 80% 未満）その状態が 5 分続くまで同じ件は再送せず、戻ったときに回復の通知を送ります。ホストがオフラインの間は判断しません。パネルを再起動しても、まだ回復していないアラートは再送しません。しきい値は固定で、変更できません。

通知は「ディスクの空き不足」「メモリ使用率が高い」「CPU 使用率が高い」を購読している通知チャネルへ送ります。既存の通知チャネルはアップグレード時に 3 つとも自動でオンになります。不要なら「設定 → 通知とボット」でオフにしてください。

## Hostower の更新

### 更新後、ページに新機能が表示されない

Hostower はシングルページアプリケーションです。サーバーが更新されて再起動した後、すでに開いているページは自動で再接続し、**設定** に表示されるバージョン番号も新しいものに変わりますが、ページ自体のコードは古いままです。`Ctrl+F5`（Mac では `Cmd+Shift+R`）で一度強制再読み込みしてください。

### なぜ設定に「このビルドには更新元が設定されていません」と表示されるのですか？

自動更新は正式リリースのバージョンでのみ有効です。リリース公開鍵で署名を検証する必要があるためです。自分でビルドしたバージョンにはリリース公開鍵がないため、バイナリやイメージを自分で置き換えて更新する必要があります。

### 初期パスワードはどこにありますか？

データディレクトリの `initial-password` ファイルにあり、ログには書き込まれません。Docker でデプロイした場合：

```bash
sudo cat data/initial-password   # compose.yaml のあるディレクトリで実行
```

ログイン後はできるだけ早くパスワードを変更し、Passkey または認証コードを追加してください。すべてのログイン手段を失った場合は、サーバー上で `hostower auth reset-password` を実行します。
