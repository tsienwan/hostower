# Hostower 设计方案

> 本文描述 Hostower v0.5.2 **当前的设计和实现**。每一节开头先说结论；功能一览见 [README](../README.zh-CN.md#功能)，威胁与对策见[威胁模型](threat-model.md)。

## 一、定位与设计原则

**Hostower 是一个开源、自托管的多主机运维灯塔：一个人或一个小团队在一处看清所有主机、对它们下达操作；每一步变更都经过确定性的风险判定和人的批准，并留下可校验的审计。** 名字是 host + tower：灯塔照得见海面上的每一条船，并为它们指引方向。

本文是通用产品设计，不包含任何具体主机、域名、账号或凭据。文中的主机名（`web-1`、`db-1`）、地址（`192.0.2.x`、`example.com`）都是文档保留值。

适用范围：

- 管理 1 到几百台 Linux 主机（VPS、物理机、家用机），单进程、单数据卷部署。
- 使用者是个人运维、独立开发者和小团队，不是大型企业的多租户平台。
- 可以只在内网访问，也可以放在公网；安全设计按公网暴露来做。

不可妥协的原则：

1. **只有一条路能触达主机**：任何入口的任何操作都走“判级 → 审批 → 执行 → 审计”，没有后门接口。例外只有两类，见[第五节](#55-两类例外)。
2. **判级只升不降**：解析失败或不认识的命令是 L1；没有任何代码路径能把 L3 放行。
3. **凭据只出现引用**：资源、日志、审计、接口响应里只有 `ref:<名称>`，凭据本体只在执行器里取出、用完即弃。
4. **默认按公网设防**：假设网络不可信、面板可能被攻破，每一层都要能单独挡住。
5. **内核没有扩展点**：判级取最高、L3 规则、审批状态机、审计写入只随正式版本变化。
6. **兼容靠迁移，不靠运行时分支**：持久化的东西都带版本号，升级时一次性迁移。
7. **仓库零敏感信息**：主机清单、凭据、部署细节都在仓库之外，示例只用保留值。

## 三、总体架构

**Hostower 是一个 Go 进程，前端编译进同一个可执行文件。所有入口汇到同一个网关，所有操作都要穿过安全内核才能到达主机。**

```
浏览器 / 命令行 / 聊天机器人 / MCP 客户端
      │
      ▼
网关 gateway ─ 认证、来源校验、会话、请求体上限、限速
      │
      ▼
安全内核 kernel ─ 判级 → 审批 → 调度执行 → 审计（哈希链 + 文件副本）
      │
      ▼
执行器 executor ─ ssh │ local │ sim（仅开发模式）
      │
      ▼
主机
```

旁路的后台组件都只通过内核的固定入口工作：

- **采样器** `metrics`：每台主机一条流式采样连接，只能运行编译进程序的只读脚本。
- **本机监测** `selfmon`：读 Hostower 所在机器的 `/proc` 和磁盘用量，不经过执行器。
- **更新器** `update`：换的是 Hostower 自己的可执行文件，不碰任何主机。

后端各包：

| 包 | 职责 |
| --- | --- |
| `cmd/hostower` | 命令行入口：`serve`、`classify`、`exec`、`audit verify`、`keygen`、`secret set-ssh`、`hostkey forget`、`healthcheck`、`version` |
| `internal/kernel` | 请求、判级、审批、执行调度、终端会话、只读查询、采样入口 |
| `internal/kernel/risk` | 基于 shell 语法树的判级引擎、内置规则、规则包、测试表 |
| `internal/kernel/audit` | 只追加的审计日志、哈希链、文件副本、分页查询 |
| `internal/executor` | 执行器接口与 SSH、本机、模拟三种实现；固定的采样命令 |
| `internal/gateway` | HTTP 接口、WebSocket、安全响应头、静态资源 |
| `internal/inventory` | 主机清单、分组与选择器、内置本机主机 |
| `internal/snippet` | Snippet 解析、参数校验、渲染与转义 |
| `internal/secrets` | 信封加密的凭据存储 |
| `internal/auth` | Passkey、密码、动态码（TOTP）的登录和身份验证，登录方式设置，会话，首次启动的初始密码 |
| `internal/metrics` | 流式采样、解析、内存历史和分级落盘 |
| `internal/gateway`（filesync） | 文件同步：分发是每个文件一个多主机的命令请求（`mkdir -p 目录 && cat > 目标`，内容从标准输入送）；收集是只读的 find 加逐个“下载文件”，打成 zip |
| `internal/hostenv` | 主机的环境检测：装了哪些 AI 命令行工具和运行环境、IPv4 和 IPv6 出口的归属和类型、AI 服务看到的地区和风控信号、各家模型接口和常用网站能不能用（全部是只读查询） |
| `internal/gateway`（agents） | Agent 协作：把一个任务派给多台主机上的 AI 编程助手（一个多主机的命令请求，非交互运行，默认只读），以及让一台主机上的助手汇总（各台输出暂存成文件，从标准输入送进去）。判级规则把跳过权限确认或沙箱的调用判成 L2 |
| `internal/selfmon` | 本机监测 |
| `internal/update` | 自我更新：检查、下载、验签、切换 |
| `internal/app` | 配置、面板设置、启动自检、组装各部件 |
| `internal/store` | SQLite 与按序迁移 |

## 四、核心模型

### 4.1 主机与分组

主机可以写在配置目录的 `inventory.yaml` 里（只读，适合放进私有 Git 仓库），也可以在页面上新增、编辑、删除（存进数据库）。名字冲突时配置文件优先。

```yaml
apiVersion: hostower/v1
kind: Inventory
hosts:
  web-1:
    addr: 192.0.2.10
    executor: ssh              # ssh | local | sim（sim 只在开发模式可用）
    credential: ref:ssh/ops    # 只写引用，不写凭据本身
    tags: [web, prod, docker]
    sensitivity: normal        # low | normal | high（high：写操作自动升一级）
    vars: { compose_root: /opt/stack }
groups:
  safe:   { selector: "* and not sensitivity:high" }
  docker: { selector: "tag:docker" }
```

- 分组可以是静态列表，也可以是选择器；新主机打上标签就自动入组。
- `sensitivity` 参与判级：高敏感主机上的写操作升一级，批量执行时强制逐台滚动并排在最后。

**内置的本机主机 `local`**：Hostower 在 Linux 上直接运行（或用宿主机版镜像）时，清单里自动有一台 `local`，不用配 SSH 就能看指标、管容器、读写文件、开终端。它的标签和敏感度可以在页面上改，名字和连接方式固定，不能删除；设置 `HOSTOWER_LOCAL=0` 可以关掉。取舍见[第九节](#九部署)。

### 4.2 凭据

**凭据集中存在 Hostower 里，用信封加密；页面和接口只写不读，资源里只出现引用名。**

| 类别 | 引用形式 | 用在哪 | 怎么送到主机 |
| --- | --- | --- | --- |
| SSH 凭据 | `ref:ssh/<名称>` | 连接主机 | 只在 SSH 执行器里解密使用 |
| 镜像仓库 | `ref:registry/<名称>` | `docker login` | 密码从标准输入送过去，不进命令行 |
| 应用密钥 | `ref:app/<名称>` | 部署容器时注入环境变量 | 写成主机上只有本人可读的环境文件，值从标准输入送过去 |

- 主密钥不进数据库。显式配置时来自 `HOSTOWER_MASTER_KEY_FILE`（或 `HOSTOWER_MASTER_KEY`）；没有配置时，第一次启动在数据目录里自动生成 `master_key`（权限 0600），做到开箱即用。
- 自动生成的主密钥和数据库在同一个目录：只泄露数据库文件时凭据仍然安全，泄露整个数据目录或它的备份时不安全。凭据页会提示这一点，并说明怎么把它移出去。
- 主密钥文件损坏时拒绝启动，不会悄悄重新生成（重新生成会让已保存的凭据全部解不开）。

### 4.3 执行器

所有上层只依赖一个接口：执行命令（流式输出，可带标准输入）、读文件、写文件、列目录、开交互终端。

| 执行器 | 连接方式 | 被管机要求 | 说明 |
| --- | --- | --- | --- |
| `ssh` | Hostower → 主机 | 只要 sshd | 连接复用；主机公钥首次信任后固定；文件走 SFTP |
| `local` | 同一台机器 | 无 | 直接运行二进制时以当前账号执行；宿主机版镜像里用 `nsenter` 进入宿主机命名空间、以 root 执行，文件经 `/proc/1/root` 读写 |
| `sim` | 无 | 无 | 只在 `--dev` 下注册，返回逼真的模拟输出，用来体验和测试 |

执行器只是通道，不做任何决策。本机执行器默认使用 UTF-8 语言环境，中文和表情符号的文件名能正常显示。

### 4.4 Snippet

Snippet 是参数化的操作模板：

- 参数有类型（`string`、`int`、`bool`、`enum`、`path`）和校验规则，页面表单由它自动生成；模板里还能引用主机变量（`.host.vars.xxx`）。`host`、`group`、`secret` 类型的参数在规划中。
- 按“参数 + 主机变量”逐台渲染出实际命令，所有参数做 shell 转义；空的可选参数渲染为空。渲染结果先预览、再判级、再执行。
- 可以放在配置目录里（只读），也可以在页面上新建、编辑，带实时渲染和判级预览，可导出 YAML。
- 审计记录当时用的 Snippet 和版本。

### 4.5 应用市场

应用是带生命周期的声明式清单（`internal/apps/catalog/*.yaml`，编进可执行文件，随发布签名一起被信任）。分两类：用 docker compose 跑的容器应用，以及装进登录账号目录（`~/.hostower/npm`、`~/.local/bin`，不用 sudo）的 npm 命令行工具；系统里的 Node.js 不够新时，下载固定版本的官方发布包并校验 SHA-256。

- 没有自己的执行通道：安装、更新、启停、卸载都渲染成每台主机上的一条命令，走 `SubmitCommand`。批量操作是一个请求，每台主机的命令（参数）可以不同，摘要覆盖每一条；只有标准输入（密钥）不同的主机才拆成几个请求。
- compose 文件的内容写在命令的 heredoc 里，所以被摘要覆盖；判级引擎检查写进 compose 文件的内容（`risk.ComposeFindings`）：特权、宿主机命名空间、内核能力、设备、敏感目录和 Docker 套接字的挂载、看不全或看不懂的内容，一律 L2。清单不能自报权限。
- 密钥只以 `ref:app/<名称>` 出现，执行时由执行器写进主机上只有登录账号可读的 `.env`（值加单引号，防止 compose 展开 `$`）。
- 已安装的状态不存数据库，以主机上的 `~/.hostower/apps/<实例>/app.json` 和带应用标签（`apps.LabelKey`）的容器为准（只读查询）。更新沿用主机上记下的参数；命令行工具的新版本面板自己去 npm 查（只带包名），查不到就只和目录里的版本比。
- AI 命令行工具的配置（Codex、Claude Code、DeepSeek Harness）：启动脚本每次运行时读实例目录里的 `config.env`（接口地址、模型，命令里可见）和 `secret.env`（API Key，只有登录账号可读，内容从标准输入写入）；Codex 和 DeepSeek Harness 的配置目录用 `CODEX_HOME`、`DSH_HOME` 指到实例目录，不碰用户自己的。供应商预置在 `internal/apps/ai.go`。DeepSeek Harness 的第三方提供商（它内置的 pi-ai 目录，或自定义的 OpenAI / Anthropic 兼容接口）写在 `$DSH_HOME/cordis.patch.yml`：只写路由、协议、地址和默认模型，Key 用 `apiKeyEnv` 指向 `secret.env` 里的变量。订阅登录走交互终端（开终端按 L2 审批、全程录制），登录命令按应用名从目录里查出来预先填好，回车由人来按。
- 检测更新：版本号以清单为准（审批绑定的是确切的镜像标签，大版本要人先确认能不能原地升级）。清单版本没变时，再拿主机上镜像的摘要和镜像仓库里同一标签的摘要比对（标准的仓库接口，匿名令牌，HEAD 请求），不一样就提示“镜像有新构建”，更新就是重新拉取；还会探测下一个大版本的标签（2 → 3、8-alpine → 9-alpine），有的话只提示“上游有新大版本”，不提供一键更新。查询结果缓存 6 小时，只带镜像名。
- 上手指南：清单的 `guide` 写明装好以后从哪里打开（协议、端口、路径）、初始账号是什么、接下来做哪几步；“已安装”列表按每个实例的参数渲染好（主机上记的参数重新校验，不合法就不显示），安装请求执行成功后也给出入口。初始账号是第一次启动时随机生成、只在日志里出现一次的应用（3x-ui），清单里给一条只读命令（`guide.reveal`），页面上点一下由内核的只读查询去读，读到的内容只显示、不保存；这条命令和别的查询一样过判级，不是 L0 就拒绝（测试里锁住每个内置应用的都是 L0）。能在安装时定下来的初始密码一律做成应用密钥（OpenList 的 admin 密码、LiteLLM 的主密钥）。
- 打开面板：清单里给网页面板的访问入口标上 `panel`（每个应用最多一个），“已安装”列表上的“打开面板”按钮按这个实例在主机上记的当前参数（监听地址、端口）和清单里的协议、路径现拼地址，改过设置以后自然跟着变；端口或路径是在应用自己的页面里改的（3x-ui），清单用 `inApp` 说明。拼不对时所有者可以给实例设一个面板地址（`apps.PanelSetting`，带版本号的 JSON，存在 settings 表的 `apps.panel:<主机>/<实例>`，`PUT /api/v1/apps/panel`）：直接访问时覆盖端口和路径、填完整地址（反向代理或域名，网络页里反代到这个端口的站点会列出来）、或经由 SSH 隧道（页面给出 `ssh -N -L` 命令，按钮打开本机端口）。它不碰主机，所以不走审批，但只有所有者能改，先写审计（`app.panel`），写不进去就不改。地址只接受 http(s)，不能带账号密码、查询参数和片段，读出来时也重新校验：按钮链接里不会出现凭据。
- 升级说明：清单的 `upgrade.note` 在更新入口提示（比如先备份）；`upgrade.blockFrom` 列出不能原地升级的旧版本（比如 PostgreSQL 17 → 18 数据目录不兼容），这些实例不提供一键更新，改设置和自动发起更新也会跳过。
- 自动发起更新（所有者打开，默认关闭）：每 6 小时检查一次，发现新版本就以“应用自动更新”（系统身份，不能批准）提交更新请求，照常等人批准。同一实例的同一版本只发起一次：等批准时不重复，被拒绝后不再提，过期或失败的隔一天再提。不做无人值守的自动更新：L1 以上的请求总要有人批准。

### 4.6 网络入口（防火墙、站点、证书、Fail2ban）

主机详情的“网络”页（`internal/netcfg`）：一段只读的检测脚本（L0）看系统、防火墙、Caddy / Nginx 和它们的站点、certbot 的证书、Fail2ban 的状态和被封的 IP、对外监听的端口和 Docker 发布的端口；改动都渲染成命令走审批。

- 防火墙用主机上已经在用的那个（ufw 或 firewalld），都没有时按系统推荐一键安装（Debian/Ubuntu 用 ufw，RHEL 系用 firewalld）；两个同时启用时不动手，只提示。改防火墙是 L2。
- 不把自己锁在外面：启用前先放行 SSH 端口（和面板对外的端口、勾选的正在监听的端口），最后才启用，任何一步失败都不启用；SSH 和面板的端口不能关。
- 需要 root 的命令写成“是 root 就直接运行，否则 sudo -n”两个完整分支，判级引擎看得到实际要做什么（不用变量拼命令名）。
- 站点用 Caddy 或 Nginx（系统软件源安装，每台主机只装一个，两个都要 80/443）。站点有反向代理（转发到 127.0.0.1 的端口）、静态目录（只能在 /var/www、/srv、/opt、/home 下，不能是隐藏目录）、跳转三种。每个站点一个文件（Caddy 在 `/etc/caddy/sites.d`，主配置里加一行 import；Nginx 是 `/etc/nginx/conf.d/hostower-*.conf`），第一行是标记，检测脚本只读标记，所以只列出 Hostower 加的站点。文件内容用带引号的 heredoc 写进命令里，审批摘要覆盖写入的全部内容；写完先 `caddy validate` / `nginx -t`，通过才重载，不通过把文件改名成 `.rejected` 撤下。删除是改名成 `.removed`。写站点是 L1。
- 改完站点用 `systemctl reload-or-restart`：服务在运行就重载，没在运行就启动。装好了但没在运行时，页面上有“启动”（L1）；启动或重载失败时，输出里带上服务最近 20 行日志。添加站点前先看站点要用的端口（地址里写的端口，否则 HTTPS 是 443、只用 HTTP 是 80）是不是被别的程序占着：检测时看得到程序名就直接拒绝，否则在命令开头用 `ss` 再查一次，被占就什么都不改。添加站点后重载失败，会撤下刚写的站点文件并重启服务回到原来的配置（Caddy 重载失败后会停在“重载中”，之后的重载和启动都会卡住）。`systemctl is-active` 报 `reloading` 也算在运行。
- HTTPS：Caddy 自动申请；Nginx 用 certbot 的 webroot 方式申请 Let's Encrypt 证书（先写 HTTP 站点让 80 端口能验证，拿到证书再换成 HTTPS 配置；不让 certbot 改 Hostower 写的文件），续期靠 certbot 自带的定时任务，续期后重载 Nginx。也可以填主机上已有证书的路径（只写进配置，不读私钥）。证书列表来自 `certbot certificates`（L0），续期是 L1，删除和吊销证书是 L2（页面不提供）。
- Fail2ban 装在宿主机上，只写 `/etc/fail2ban/jail.d/hostower.local`。它管着防火墙的封禁规则，所以 `/etc/fail2ban` 算关键配置，`fail2ban-client` 除了查看（status、get 等）都是 L2，fail2ban 服务的启停也是 L2：安装、改设置、解封都要在网页上批准。不把自己封掉：白名单固定有回环地址和 Hostower 的来源地址（`SSH_CONNECTION`）；安装时先写配置再装包，服务第一次启动就带着白名单；改设置先备份，`fail2ban-client -t` 不通过就换回去。
- Docker 直接发布到所有地址的端口会绕过 ufw 和 firewalld：页面列出来提醒改绑 127.0.0.1。云服务商的安全组在主机之外，管不到。

## 五、安全内核

**内核是唯一能触达主机的路径：判级、审批、执行、审计四步，代码量小、无扩展点、由测试表锁定行为。**

### 5.1 风险分级

| 等级 | 含义 | 示例 | 处理 |
| --- | --- | --- | --- |
| L0 | 只读 | `df -h`、`docker ps`、读普通文件 | 自动执行 |
| L1 | 变更 | 装包、改配置、重启服务、写文件 | 一人批准 |
| L2 | 高危 | 删数据、改防火墙或 sshd、重启主机、开交互终端 | 网页上当场用 Passkey 或动态码验证身份，并输入主机名 |
| L3 | 禁止 | `rm -rf /`、写块设备、读私钥、`curl … \| sh` | 直接拒绝，任何角色、任何入口都不能放行 |

判级规则：

- 用 shell 语法解析器把管道、`&&`、命令替换、子 shell、`sh -c`、`eval`、heredoc 拆成单条命令，剥掉 `sudo`、`env`、`xargs` 这类包装，逐条匹配规则，取最高等级。
- 解析失败或不认识的命令按 L1，绝不降级。
- 最终等级 = max（命令判级，Snippet 声明等级，主机敏感度加成）。
- 规则包（YAML）只能加严，不能放宽。
- 行为由[测试表](../internal/kernel/risk/testdata/table.txt)锁定：任何规则改动都先改表、再改代码。表里也包括页面上会生成的所有固定命令（容器操作、文件上传、采样脚本等），确保它们的等级不会悄悄变化。

### 5.2 审批

- 审批卡片展示**渲染后的实际命令**（或文件的 diff）、目标主机、判级理由、标准输入的说明（例如“上传的文件 xxx，大小、SHA-256”）。
- 批准绑定请求摘要：摘要覆盖每台主机上的实际命令、文件内容、标准输入的身份（换了文件或凭据，批准作废）。待批准的请求 30 分钟后过期。
- 发起人是 AI 或自动化时，批准人必须是人；L2 只能在网页上批准。
- 紧急开关：一键暂停全部执行（同时断开终端和采样连接）、一键吊销所有会话。

### 5.3 执行策略

- 批量执行有并发上限，可以先在一台上预演、遇错停止。
- 目标里有高敏感主机时强制逐台滚动，高敏感主机排在最后。
- 写文件时先备份旧内容；提交后旧内容变了，批准作废。

### 5.4 审计

- **只追加**：没有修改接口，数据库触发器拒绝改写；写审计失败时操作中止。
- **归档后清理**：所有者可以在“设置 → 安全 → 审计”里设一个条件（默认关闭）：数据库里的记录超过 1 万～100 万条时，把早于 30 天～2 年的记录归档。每 6 小时检查一次，也可以手动“现在检查一次”。归档按顺序做：重新校验这一段的链 → 写进数据目录的 `audit-archive/audit-<起>-<止>.jsonl.gz`（先写临时文件、落盘、再改名）→ 在链里追加一条 `audit.archived`（写不进去就停）→ 在只追加的 `audit_checkpoints` 表里记下检查点（最后一条的哈希、文件摘要）→ 删除数据库里检查点之前的记录。触发器只允许删检查点之前的记录。之后的校验从检查点接着算；`hostower audit verify` 会同时校验每个归档文件的摘要和首尾相接。归档的记录不在审计页上显示。删除的空间由 SQLite 留给之后的新数据复用，数据库文件不会自己变小。数据目录里的 `audit.jsonl` 是另一份独立副本，不随归档清理。
- **哈希链**：每条记录包含上一条的哈希，可以在页面上或用 `hostower audit verify` 离线校验。
- **文件副本**：同时写一份 JSONL 到数据目录，便于转存到外部。
- **范围**：**关键操作永远记录**（登录、提交、批准、每次执行、开终端、读取和下载文件内容、上传、改设置等）。**日常查看默认不记**（翻目录，以及列容器、看容器日志和配置、搜文件这类只读查询）：它们数量很多，会淹没关键操作。所有者可以在“设置 → 审计”里打开记录，开关的每次改动本身都写审计。这是审计写入上唯一的开关。
- **查看**：审计页分页显示，可以按人、主机、命令、事件名搜索；默认只显示关键操作，切到“全部”可以看到已记录的日常查看。

### 5.5 两类例外

只有这两类不逐条判级，都写在[威胁模型](threat-model.md)里，不再增加第三类：

1. **固定的只读采样**：采样命令和脚本是编译期常量，内核启动时确认它们被判为 L0，否则拒绝启动；不逐次写审计；暂停全部执行时立刻停止。脚本里会运行可选的增强采集程序（见 6.4）：它是经过审批装到固定位置的、只读的程序。
2. **交互终端**：终端里敲的命令无法逐条判级，所以“打开终端”本身固定按 L2 处理，只有人能开，整段输出录制成 asciicast 文件，开始和结束写审计；长时间无操作自动断开。

## 六、指标采样

**每台主机一条 SSH 长连接，主机上运行一段固定的只读脚本，每 5 秒输出一轮；主机上不需要安装任何东西。** 这是在“零安装”和“开销低、及时、准确”之间权衡后的方案。

### 6.1 方案对比

| 做法 | 被采集端压力 | 中心压力 | 及时性 | 准确性 | 要不要装东西 |
| --- | --- | --- | --- | --- | --- |
| 定时连上去跑一次命令（早期做法） | 每次启动十几个进程 | 反复建会话 | 30 秒 | 受网络延迟影响 | 不用 |
| 装专门的采集程序（Prometheus node_exporter 拉取、Telegraf 推送等） | 最低 | 最低 | 可到 1 秒 | 最好 | 每台都要装、要升级 |
| **一条长连接持续输出（现在）** | 每轮只启动一个 `sleep` | 每台一条连接、一个协程 | 5 秒 | 按主机自己的时钟计算 | 不用 |

### 6.2 工作方式

- 脚本读 `/proc` 全部用 shell 内建命令（`read`、`echo`、`case`），不启动进程；每十二轮（一分钟）才跑一次 `df`，系统信息和进程数这类变化慢的段落也每分钟才输出一次，其余时候沿用上一次的值。
- 每轮以单独一行 `===` 结束；采样器按轮切分、解析，收到一轮就记一个点。
- **准确性**：CPU、网络、磁盘读写都用累计值相减；两轮之间的间隔用主机自己的开机时长来算，不受网络抖动影响。
- **可靠性**：看门狗发现连续 20 秒没有新的一轮就判定断开；断开后记为离线并重连，失败时退避到最长一分钟。连接断开时主机上的脚本随会话一起退出，不留残余进程。
- **容器占用**也在同一个脚本里：直接读每个容器的 cgroup 文件（累计 CPU、内存、可回收缓存）和它的网络计数，和主机指标一样 5 秒一轮、不启动进程；容器名每分钟用一次 `docker ps` 取。数值和 `docker stats` 一致（实测 CPU 14.3% 对 14.47%，内存 7013 MB 对 7015 MB），但不再调用它——那条命令自己要跑一两秒。支持 cgroup v2 和 v1、systemd 和 cgroupfs 两种驱动；都读不到时退回每分钟一次的 `docker stats`。
- 实测：一台 Debian 主机上，脚本运行几分钟累计 CPU 时间为 0、常驻内存约 1.4 MB，几分钟内只建立了一次 SSH 登录。

### 6.3 指标与历史

- 指标：CPU、内存与缓存、交换分区、1/5/15 分钟负载、根分区与各分区占用、磁盘读写速率、网络收发速率、温度、进程数、开机时长、系统与内核版本、每个容器的 CPU / 内存 / 网络。
- 硬件：CPU 厂家、型号、颗数 / 核数 / 线程数、基础与最高频率、三级缓存、架构；整机厂家和型号（云主机通常是实例规格）、主板；是物理机还是虚拟机（及虚拟化平台）；各块磁盘的容量、型号、固态还是机械。连上主机时读一次，之后每 6 小时一次，显示在主机详情的“硬件”卡片里。内存条型号和频率要 root 运行 `dmidecode` 才能读到，不读。
- 历史：内存里保留最近 90 个点用于“实时”；落盘分两级——每分钟一个平均值，默认保留 1 天（设置里可选 1～14 天）；每 15 分钟一个，默认保留 35 天（可选 7 天～2 年）。页面可选实时、1 小时、6 小时、24 小时、7 天、30 天，保留够长时还有 90 天、1 年；分钟级数据覆盖得到的范围用分钟级画。改保留时长只有所有者能做，写审计；缩短后超出的部分在一小时内删掉。
- 和常见工具的采样间隔对比：Netdata 1 秒、Prometheus 通常 15 秒、Beszel 约 1 分钟、Zabbix 通常 60 秒；Hostower 5 秒。

### 6.4 可选的增强采集程序

**基础指标不需要它；它提供脚本做不了的东西，目前是进程占用排行。** 它是一个约 2 MB 的静态程序（`cmd/hostower-agent`），按需装到主机上。

- **不开端口、不常驻、没有配置**：采样脚本每分钟看一眼主机上的固定位置（`~/.hostower/bin/hostower-agent`）有没有它，有就在同一条 SSH 连接上运行它；它输出和脚本完全相同格式的数据，外加进程排行和自己的版本。连接断了它就退出。
- **随时可以没有它**：它起不来、被删掉、版本被换掉时自己退出，脚本在同一条连接上接着采。所以装不装，用的是同一条连接、同一套解析，基础指标不会因为它出问题而中断。
- **在面板上安装**：主机详情的“进程”卡片里点“安装增强采集”。Hostower 先读主机的处理器架构，取出自己带着的那一份（amd64 或 arm64），生成一个 L1 请求：程序内容从标准输入写到主机上，请求摘要绑定它的大小和 SHA-256，批准后才执行。卸载是删除文件，按 L2 处理。
- **来源**：采集程序在构建 Hostower 之前编译（`go run ./tools/buildagent`），再被编译进 Hostower 的可执行文件里，不从网络下载。所以它的完整性和 Hostower 本身一致，自我更新之后带的也是新版本；页面发现主机上的版本和自己不一致时提示更新。
- **判级**：只有“固定位置 + 固定参数 `stream`”这一种调用被判为只读（L0），所以它可以放进固定的采样脚本里；别的路径上的同名程序、别的参数仍按变更处理。
- **开销**：实测运行时累计 CPU 时间接近 0，常驻内存约 3–7 MB。

### 7.1 文件预览

**主机上的文件一律当不可信内容：由页面自己解析成纯数据再显示，浏览器不会把它当网页打开，内容安全策略也不用放宽。**

| 类型 | 怎么显示 | 显示什么、不显示什么 |
| --- | --- | --- |
| 图片（png、jpg、gif、webp、bmp、ico、avif、svg） | 转成 `data:` 地址放进 `<img>` | 适应宽度或原始大小；SVG 在 `<img>` 里不会执行脚本 |
| PDF | pdf.js 画到 canvas 上 | 前 50 页；不用浏览器内置阅读器、不放进 iframe，不渲染表单、不运行文档脚本 |
| Markdown | 渲染成 React 元素（支持表格、任务列表） | 原始 HTML 不解析；外部图片不加载，只显示说明文字；只有 http(s) 链接可以点 |
| CSV / TSV | 解析成表格 | 处理引号、逗号和换行；最多 1000 行、60 列；可以切到源码 |
| Excel（xlsx） | 解压后读 XML，取单元格文字 | 多个工作表可切换；最多 1000 行、60 列；不算公式、不套数字格式（日期显示为数字） |
| Word（docx） | 同上，取段落和表格 | 标题、加粗、斜体、列表、表格；图片、排版、批注不显示 |
| PowerPoint（pptx） | 同上，取每一页的文字 | 标题、正文、表格、演讲者备注；图片、版式、动画不显示 |
| 旧版 Office（doc、xls、ppt） | 不预览 | 提示下载或另存为新格式 |

- 文件通过和下载同一个接口取回（`preview=1`），上限 20 MB，审计里记为“读文件”；私钥、凭据文件照样读不了。
- Markdown 和 CSV 走原来读文本的接口，可以在“预览 / 源码”之间切换，也可以编辑。
- 解析库按需加载：只有打开对应类型的文件时才下载（PDF 的解析器约 1.3 MB，Office 的约 10 KB）。

### 7.2 通知

**通知只是“告诉你该去看一眼”。** 消息里只有摘要和一个回到页面的链接；在聊天里能做的事另有一个受限的入口（7.3），批准永远要回到网页上。

| 渠道 | 需要填的 | 怎么发 |
| --- | --- | --- |
| Telegram 机器人 | Bot Token、Chat ID（个人、群组或 `@频道`） | `sendMessage`，纯文本，不展开网页预览 |
| 飞书机器人 | 自定义机器人的 Webhook 地址；可选签名密钥 | 富文本（post）消息，开了签名校验时带时间戳和 HMAC 签名；Lark 国际版同样支持 |
| Discord | 频道的 Webhook 地址 | 卡片（embed），左侧竖线按严重程度着色；关掉所有提及解析 |
| 邮件 | SMTP 服务器、端口、加密方式（SSL/TLS、STARTTLS，或在 25 端口不加密且不登录）、账号、发件人、收件人 | 纯文本邮件，UTF-8，标题带 `[Hostower]` |

可订阅的事件（括号里是默认是否勾选）：

| 分组 | 事件 |
| --- | --- |
| 请求 | 有请求等待批准（是）、请求执行失败（是）、请求执行完成（否，L0 永远不发）、请求被拒绝（是） |
| 主机 | 主机离线（是，连续离线 2 分钟才发）、主机恢复在线（是，只在发过离线之后） |
| 安全 | 登录失败（是）、有人打开终端（否）、紧急开关与吊销会话（是）、凭据被修改或删除（否） |
| 系统 | 系统更新结果（是） |

- **来源**：请求和主机状态来自内核的事件订阅；安全类事件来自审计（通知中心是审计的一个外部副本接收端），所以“发生了”就一定有对应的审计记录。
- **范围**：每个渠道可以只看某些主机；不填就是全部。每个渠道单独选语言（中文或英文）。
- **不打扰**：同一条通知一分钟内只发一次；每个渠道每分钟最多 20 条，超出的丢弃并记日志；失败重试 3 次，最后一次的错误显示在设置页里。
- **不拖慢主流程**：发送在独立的队列里进行，队列满了就丢弃；写审计、执行请求永远不等通知。
- **机密**：Token、Webhook 地址、签名密钥、SMTP 密码存进凭据库（`notify/<渠道>`，和 SSH 凭据同一把主密钥加密），只写不读；修改时留空就沿用原来的。
- **管理**：只有所有者能新增、修改、删除渠道和发测试通知，这些操作都写审计。

### 7.3 聊天命令（Telegram）

所有者可以把自己的 Telegram 账号绑定到 Hostower，私聊机器人做几件不需要 Passkey 的事。默认关闭。

| 能做 | 不能做 |
| --- | --- |
| `/status` 主机在线情况、是否暂停、待批准数量 | 批准任何请求（聊天入口的 Actor 没有批准权；L2 本来就只能在网页上批准） |
| `/pending`、`/failed` 等待批准的请求、最近 24 小时失败的执行（带回到页面的链接） | 恢复执行（只有 `/pause`，没有恢复） |
| `/run 主机[,主机] 命令` 走和网页同一个 `SubmitCommand`：L0 直接执行，最多等 30 秒把截断后的输出发回；L1、L2 生成请求，回到网页批准；L3 被拒绝 | 开终端、读写文件、改设置、改凭据、管理容器 |
| `/pause` 紧急暂停全部执行；`/unbind` 解除绑定 | 在群组、频道里使用；别人发的消息一律不回应 |

- **绑定**：只能由已经用 Passkey 登录的所有者在网页上生成一次性配对码（8 位，5 分钟有效，只能用一次，输错 5 次作废），再私聊机器人发 `/bind 配对码`。绑定记下 Telegram 用户编号和它代表的 Hostower 账号。
- **认人**：只认私聊，且发送者的用户编号必须等于绑定的那个（这个编号由 Telegram 服务器填写，别人冒充不了）。每条消息都重新检查：绑定有没有过期、对应的 Hostower 账号还在不在、是不是仍然是所有者。
- **有效期**：默认 30 天，可以在设置里改（1–365 天），改动对现有绑定立即生效。过期后要回网页重新配对。“吊销所有会话”会一起解除绑定；换一个机器人也会解除。
- **收消息**：Hostower 主动向 Telegram 长轮询，不在公网开放回调接口；启动时跳过积压的消息，超过 2 分钟的旧消息不处理。
- **留痕与限流**：每条命令都先写审计（入口记为 `chat`），写不进去就不执行；绑定、解绑、过期、配对码输错、设置改动都写审计，配对码输错还会触发“登录失败”通知。每分钟最多 20 条命令。
- **机器人**：借用一个 Telegram 通知渠道的机器人（令牌仍然只在通知中心里）。建议给 Hostower 单独建一个机器人：同一个机器人不能同时被两个程序接收消息。

### 7.4 测速

- 单台（主机详情的“测速”按钮）或多台（“测速”页，勾选或全部在线主机）一起测；多台是一个请求、一次批准，最多 4 台同时进行。
- 主机上用 curl 连 Cloudflare 的测速服务（speed.cloudflare.com）：先取一份 trace（出口 IP、地区、节点、TLS 版本）；连五次，分段记下域名解析、TCP 握手、TLS 握手、等首字节，延迟取 TCP 握手最快的一次；下载 10 / 25 / 100 MB，上传是下载量的四分之一，记下传输量、用时和首字节时间。
- 可选顺便做路由追踪：对所有者在测速页设定的目标（最多 6 个，IP 或域名，默认只有测速节点）各跑一次 `traceroute -n`（没有就用 `tracepath -n`）。线路按几段公开的运营商骨干网段推测（电信 CN2 / 163 / CTGNet、联通 9929 / 4837、移动 CMIN2 / CMI / CMNET；地址段认不出的按节点所属的自治系统补上；163 骨干只认 202.97.0.0/16，按自治系统号 AS4134 认出的只算“电信”（各省城域网也在里面）；163 骨干出现在 CN2 那一段的外侧算 GT，否则算 GIA，只有一跳、前后两侧是同一张网的零星地址（夹在 CN2 中间的单个 163，或夹在 163 中间的单个 CN2）不算换网），不联网查询，只作参考。看回程线路需要把目标设成自己那边的地址。弹窗里的检查（`for c in curl traceroute tracepath; do command -v "$c"; done`，L0）会一并看有没有 traceroute 或 tracepath；都没有时可以勾选顺便安装 traceroute，和安装 curl 在同一个请求里（L1），装不上不影响测速。改目标先写审计（`speedtest.routes`）。 <!-- hygiene:allow：公开的骨干网段 -->
- 它会从主机往外收发数据、消耗流量，所以判为 L1，要批准才执行；命令是固定的，测速服务把请求里的命令和自己生成的比对过才解析结果。
- 打开测速弹窗时先用只读查询（`command -v curl`，L0）看哪些主机没有 curl；可以勾选“先自动安装 curl”，用系统的包管理器（apt、dnf、yum、apk、zypper、pacman）装好再测，需要 root 或免密 sudo。安装和测速是同一个请求（安装软件包同样是 L1），批准一次。
- 整个流程在一个弹窗里：选数据量和是否安装 → 核对实际命令并在弹窗里批准（L2 时同样要 Passkey 和输入确认）→ 看各台的进度和结果；关掉弹窗也会在后台继续。
- 结果从请求的输出里解析，存在 `speedtests` 表里；明细（各次连接、传输、网络信息、路由）存成带版本号的 JSON，点历史里的一条打开“测速报告”。保留规则由所有者在测速页设定：每台主机最多留 10～500 条（默认 100），可选再删掉早于 7 天～1 年的（默认不按时间删）；每小时和每次有新结果时按规则清理。所有者也可以删单条或清空。这些都只是测速结果的副本，对应的请求和输出仍在审计里；改规则和删除都先写审计（`speedtest.retention`、`speedtest.deleted`）。

### 7.5 单点登录（OIDC）

- 设置 → 安全里配：签发方地址（必须 https）、客户端编号、客户端密钥（存在凭据存储，只写不读；公开客户端可以不填）、允许登录的账号（经过身份提供方验证的邮箱，或 `sub:<编号>`）、登录按钮的名字。回调地址是“访问地址 + /api/v1/auth/oidc/callback”。
- 授权码 + PKCE，state 只能用一次且要和只给回调路径用的 Cookie 对上，nonce、签名、签发方、受众、有效期都校验。
- 只替代登录这一步：登录后是所有者的会话；L2 的当场验证仍然要 Passkey 或动态码。成功、失败和设置的每次修改都写审计。
- 依赖：`github.com/coreos/go-oidc/v3` 和 `golang.org/x/oauth2`。身份令牌的签名校验、密钥轮换、算法限制容易写错，用广泛审阅过的库比自己写更安全。

### 7.6 MCP 入口（外部 AI 助手）

Claude Code、Codex 这类支持 MCP 的 AI 助手可以连到 `POST /mcp`，用工具查看主机、提交命令。批准仍然只在网页上。

| 工具 | 作用 |
| --- | --- |
| `list_hosts` | 主机名、标签、敏感度、执行方式、凭据引用（只有 `ref:名称`）、在线状态 |
| `host_metrics` | 一台主机最近一次采样：CPU、内存、磁盘、负载、网络速率、各挂载点用量 |
| `classify_command` | 预估一条命令在这些主机上的等级和理由，不提交、不碰主机 |
| `submit_command` | 主机、命令、意图（必填）→ 和网页同一个 `plan` 和 `SubmitCommand`：L0 直接执行；L1、L2 生成请求，回网页批准；L3 被拒绝。返回请求编号和网页上的批准链接 |
| `get_request` | 状态、每台主机的退出码和输出（遮蔽凭据，最多 16 KB 末尾）；`wait_seconds` 最多等 25 秒 |
| `list_requests`、`cancel_request` | 只列出、只能取消用同一个令牌提交的请求 |

没有批准、拒绝、终端、读写文件、凭据、Snippet 编辑、暂停恢复、设置类的工具。

- **传输**：MCP 的 Streamable HTTP，和面板同一个端口；每次 POST 一条 JSON-RPC 消息，回一个 JSON，不开 SSE 流，不保存会话。`GET`、`DELETE /mcp` 回 405。
- **令牌**：所有者在“设置 → 安全 → MCP 接入”签发，签发前要验证身份；名称只能用字母、数字、点、横线、下划线，不能重复，会作为发起人名称出现在请求和审计里。令牌以 `hto_` 开头，只显示一次，库里只存 SHA-256 摘要（`mcp_tokens` 表）。有效期 7、30（默认）、90、365 天或永久，可以随时吊销；“吊销所有会话”会一起吊销。最多 20 个。
- **认证**：经过网关的同一个包装（`gateway.guard`）：请求体上限 1 MB；只认 `Authorization: Bearer`，不认 Cookie；带 Origin 头时必须是本站。每次都重新检查令牌没过期、签发人仍然是所有者。认证失败按来源限速，每个令牌每分钟最多 60 次调用。
- **发起人**：`Kind: "ai"`、`Entry: "mcp"`、`CanApprove: false`，编号是签发人的编号（双人批准时 L2 仍要另一个人批），名称是令牌名称。
- **留痕**：每次工具调用先写一条 `mcp.call`（工具名和遮蔽后的参数），写不进去就不执行；请求本身由内核照常记录；签发、吊销写 `mcp.token.created`、`mcp.token.revoked`。
- **接入示例**：Claude Code 用 `claude mcp add --transport http hostower <访问地址>/mcp --header "Authorization: Bearer <令牌>"`；Codex 在 `~/.codex/config.toml` 里写 `[mcp_servers.hostower]`、`url` 和 `bearer_token_env_var`。设置页里有现成的、填好地址的示例。

## 八、公网访问安全

**这个系统等于“所有主机的钥匙”，所以按“直接暴露在公网、且 Hostower 本身可能被攻破”来设计。** 完整的威胁与对策表见[威胁模型](threat-model.md)，这里只列要点。

三种暴露方式，按推荐顺序：

1. **只在本机或私网访问**（默认）：监听 `127.0.0.1:18443`。
2. **放在会验证身份的反向代理或隧道之后**：`HOSTOWER_TLS=proxy`，`HOSTOWER_PUBLIC_URL=https://…`。
3. **自己终结 TLS**：配置证书和私钥，只接受 TLS 1.3。

已经有的对策：

- **启动自检**：对外监听却没有 TLS、开发模式对外监听、开发模式用了外部域名，都拒绝启动。
- **会话**：Cookie `HttpOnly` + `SameSite=Strict`（https 下 `Secure`）；写请求校验 Origin 和自定义头；WebSocket 校验 Origin；会话可一键全部吊销。
- **认证**：登录方式有 Passkey、密码（绑了动态码时还要再输动态码）、OIDC 单点登录；所有者在“设置 → 安全”里开关它们、设默认登录方式和默认验证方式，服务端拒绝会让自己登录不进来的设置。动态码（TOTP，RFC 6238）只作第二道和身份验证，不能单独登录。认证接口按来源限速，同一账号连续失败 5 次后开始等待（1 分钟起，翻倍，最多 15 分钟）；成功和失败都入审计。
- **身份验证**：改登录方式、密码、动态码、Passkey、单点登录设置之前要先验证身份，5 分钟内有效。账号有 Passkey 或动态码时只能用它们；两样都没有才用密码；什么都没有（只用单点登录）时，刚登录 5 分钟内算验证过。批准 L2 要当场用 Passkey 或动态码验证，一次验证只能批一次，密码不算。
- **跨站脚本**：严格的内容安全策略（不允许内联脚本、不加载第三方来源，字体也随程序打包）；远端内容一律按纯文本渲染。
- **下载**：一律以附件形式返回，不让浏览器把主机上的文件当网页打开。

目前没有的：SSH 短期证书、多用户与细粒度权限、外部审计接收端、外部安全评审。所以在通过外部安全评审之前，建议只在内网或放在会验证身份的反向代理之后使用。

## 九、部署

**三种部署方式，差别在“能不能开箱管理 Hostower 所在的这台机器”和“隔离有多强”。**

| 方式 | 内置本机 `local` | 运行身份 | 隔离 | 适合 |
| --- | --- | --- | --- | --- |
| 默认镜像（[compose.yaml](../deploy/compose.yaml)） | 没有 | 非 root，无 shell，只读根文件系统，去掉全部权限 | 最好 | 只管别的主机；宿主机当作一台普通 SSH 主机加进来 |
| 宿主机版镜像（[compose.host.yaml](../deploy/compose.host.yaml)） | 有 | 特权容器、共用宿主机进程空间，本机命令以 root 执行 | 最弱 | 想用容器部署又要开箱管理本机 |
| 直接运行二进制（[hostower.service](../deploy/hostower.service)） | 有 | 专用账号（需要管容器就加入 `docker` 组） | 中等 | 想开箱管理本机、又不想给容器特权 |

共同点：

- 一个数据卷（数据库、审计副本、终端录像、上传暂存、更新暂存）；主密钥默认自动生成在数据卷里，公网部署建议移出来单独保管。
- 首次启动自动创建所有者，用户名默认 `admin`（`HOSTOWER_ADMIN_USER` 可以换；之后可在“设置 → 安全”里改名，要验证身份并写审计，账号编号不变），生成 32 位随机密码写进数据目录的 `initial-password`（0600，不写日志）；改过密码后文件删除。页面在改掉初始密码之前一直提示。兜底是命令行 `hostower auth reset-password`：重新生成密码、打开密码登录、吊销所有会话，并写审计。
- 面板设置（监听、访问地址、TLS、会话时长）可以在页面上改，环境变量优先；写错导致起不来时用 `HOSTOWER_IGNORE_PANEL=1` 跳过。
- 开发模式 `--dev`：只能监听本机，注册模拟主机，可以用启动令牌直接登录。

### 9.1 自我更新

**新版本的可执行文件放进数据目录，验证发布签名后进程原地切换过去；容器和镜像都不用动，三种部署方式一样。**

- 设置页有“自动更新”开关（默认关闭）。打开后每隔几小时检查一次发布页，有新版本就下载、验签、切换；也可以手动“检查更新”和“更新到某个版本”。
- 信任的根是编译进可执行文件的发布公钥：签名对不上就什么都不换，并记审计。还会核对文件自己报出的版本号，防止拿旧版本冒充新版本。
- 切换后没能成功启动的版本，下次启动时会被丢弃。容器重启后，镜像里的旧版本会验签后接力到数据目录里的新版本。
- 只认 `v1.2.3` 这样的正式版本；自己编译的、没有配置发布公钥的构建不会自我更新。
- 发布由 [release.yml](../.github/workflows/release.yml) 完成：打标签后构建 amd64 / arm64 的可执行文件并签名，同时推送默认镜像和宿主机版镜像。

已知局限：宿主机版镜像里自带的 `docker` 命令不会随自我更新而更新；数据库升级了结构的版本不能直接退回旧版本（更新前还没有自动备份）。

### 9.2 兼容

- **数据库**：`internal/store` 里按序追加迁移（目前 v1–v5：基础表、页面管理的主机、页面管理的 Snippet、指标历史、更多指标列），只进不退；运行时代码只认当前格式。
- **配置文件**：主机清单、Snippet、规则包都带 `apiVersion`。
- **审计**：历史记录永不改写（改写会破坏哈希链）。
- **界面文案**：服务端只输出中文原文，由界面在显示时翻译，所以写进审计的文字也能显示成英文。

## 十、界面设计

**向苹果的设计语言学习：内容优先、中性的底、层次靠留白和字重、克制的颜色。**

- **去掉装饰**：没有动态背景、渐变和发光。浅色是暖灰底配白色面板，深色是纯黑底配深灰面板。
- **颜色只表达状态**：一个蓝色强调色（主按钮、选中、焦点）；绿、黄、橙、红只用于状态和风险等级，并且总有文字或图标同时表达，不只靠颜色。
- **字体**：系统字体优先（苹果设备上是 SF，其他系统用随包的 Inter 和思源黑体）；等宽字体只用在命令、路径、主机名这些原样内容上。全部字体随程序打包，不依赖外部来源。
- **控件**：胶囊形按钮和标签、分段控件式的页签、系统样式的开关、半透明顶栏；表格只有很淡的行线，表头可点击排序；长列表分页。
- **布局**：表格和图表为主的页面铺满宽度；表单为主的页面限宽以便阅读；宽屏下指标卡排成一行六张；适配手机宽度。
- **多语言与时区**：简体中文、繁体中文、英语、日语、韩语、法语、德语，默认跟随浏览器（缺译文时繁体退到简体原文、其他语言退到英文）；侧栏底部显示当前时间；时区默认跟随设备，可以在设置里改；所有时间显示到秒。支持的语言只登记在 `web/src/locales/languages.json`（界面、通知、聊天机器人共用）；通知和机器人的译文在 `internal/i18n/text/<语言>.json`。`go run ./tools/i18n` 核对每种语言的词典和词表是否齐全、占位符是否一致，提交前钩子和 CI 都跑。

## 十一、性能

**目标是一个小进程带动几百台主机：空闲时几乎不占资源，批量操作时瓶颈在网络和被管机。** 下表是设计目标，其中只有判级有基准测试在 CI 里跑。

| 指标 | 目标 |
| --- | --- |
| 判级一条命令 | 1 毫秒以内（CI 基准） |
| 空闲内存（50 台主机） | 100 MB 以内 |
| 冷启动到可用 | 2 秒以内（不含数据迁移） |
| 被采集端开销 | 每 5 秒一轮，不启动进程（除 `sleep`） |

实现手段：单个静态二进制（`CGO_ENABLED=0`）；每台主机一条复用的 SSH 连接，采样会话占用期间连接不会被当作空闲关闭；命令输出全程流式、有上限；批量执行有界并发；SQLite（WAL，单写连接）；前端按路由拆包，终端懒加载。

## 十二、技术栈

| 层 | 选型 |
| --- | --- |
| 后端 | Go（标准库为主）；`golang.org/x/crypto/ssh`、`pkg/sftp`、`mvdan.cc/sh`（判级的语法树）、`modernc.org/sqlite`（纯 Go）、`go-webauthn/webauthn`、`coder/websocket`、`gopkg.in/yaml.v3` |
| 接口 | `/api/v1` 下的 HTTP/JSON；实时事件和终端走 WebSocket |
| 前端 | React、TypeScript、Vite；`react-router-dom`、`lucide-react` 图标、xterm.js 终端、pdf.js（PDF 预览）、react-markdown（Markdown 预览）、fflate（解压 Office 文档）；Inter、Geist Mono、思源黑体随包 |
| 存储 | SQLite（WAL）；审计另有 JSONL 文件副本 |
| 加密 | 标准库 AEAD 做信封加密；ed25519 做发布签名 |
| 发布 | 多架构容器镜像（默认版、宿主机版）；签名的可执行文件，末尾带构建封签（程序启动时自我校验，界面显示“官方构建”和发布公钥指纹） |

另外：接口是普通的 HTTP/JSON；文件编辑用的是简单文本框；没有 OpenTelemetry 和 Prometheus 格式的自身指标端点。

## 十三、开源与仓库卫生

**仓库里只有代码、通用示例和文档；任何人克隆下来都看不出作者有哪些主机、用什么域名、凭据存在哪。**

- 真实的主机清单、Snippet、凭据、部署记录都在仓库之外，通过配置目录和数据卷读取。
- 示例只用保留值：`192.0.2.0/24`、`198.51.100.0/24`、`203.0.113.0/24`、`example.com`、`web-1` 这类角色名。
- 测试不碰真机：用模拟执行器，测试密钥在运行时生成。
- `go run ./tools/hygiene` 检查密钥、非保留网段的 IP、非示例域名和不该提交的文件；`go run ./tools/i18n` 检查多语言有没有漏。提交前钩子和 CI 都跑。
